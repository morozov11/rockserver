# Общий roadmap: интернет-бета и единый пользовательский контур

**Статус:** планирование; реализация по этому документу не начата.  
**Владение:** RockServer — центральный API и данные; RockCast, RockMobile и будущий ESP32 —
клиенты.  
**Текущий приоритет:** MVP-001 → RM-007 → RM-011 → RM-012. Другие задачи не отменены, но не должны
блокировать этот маршрут.

Конкретная последовательность реализации, зависимости, владельцы репозиториев и критерии

## Цель

До появления ESP32 подготовить RockServer к безопасной интернет-бете и проверить на реальных
пользователях единый сценарий: регистрация, вход, устройство, избранное, история, настройки и
управление воспроизведением. RockServer является сетевым источником учётных записей, синхронизации
и AI-возможностей. RockCast и RockMobile должны сохранять локальное воспроизведение при его
недоступности. Будущий ESP32 подключается к тому же контуру как простое устройство управления,
а не как отдельная система пользователей.

## Общие правила

- Внутренний идентификатор пользователя, станции и устройства стабилен и не зависит от URL потока.
- Анонимный режим и локальные каталог/воспроизведение остаются рабочими.
- Авторизация, регистрация, управление устройствами и синхронизация идут только по HTTPS.
- Секреты, refresh-токены и пароли не попадают в логи, git или прошивку ESP32.
- Права и API сначала проектируются и тестируются в RockServer; клиенты используют один
  версионированный HTTP-контракт.
- Официальный клиент не содержит общего Bearer token, ключей Yandex или других секретов.
  Пользователь не вводит адрес RockServer для обычного радио, поиска или голоса.

## MVP-001 — Анонимный публичный контур без ручной настройки

**Зачем:** дать новому пользователю работающий продукт сразу после установки: без URL сервера,
Bearer token, регистрации или отдельной инструкции. Это не заменяет будущую авторизацию: она
останется нужна для синхронизации и управления своими устройствами.

**RockServer:**

- явно выделить безопасные публичные `/v1` endpoints для пользовательского каталога/поиска и
  голосовой команды; административные, учётные и будущие sync/device endpoints остаются
  авторизованными;
- ограничить публичный доступ rate limit, лимитами размера и длительности аудио, параллельных
  voice sessions и ресурсного бюджета; не принимать доверительный «общий секрет» из клиента;
- оставить ключи SpeechKit только на сервере, журналировать только безопасные технические события
  и добавить наблюдаемость за отказами и злоупотреблением;
- при недоступности сервера возвращать предсказуемую ошибку, не затрагивающую локальное радио.

**RockCast и RockMobile:**

- официальный release имеет встроенный production base URL; UI не показывает URL или токен в
  нормальном пользовательском режиме;
- локальный каталог и воспроизведение остаются первым fallback при недоступности публичного API;
- override адреса и явный токен допускаются только в developer/test configuration, отдельно от
  пользовательских настроек.

**Готово, когда:** новый пользователь устанавливает RockCast или RockMobile, выбирает станцию,
выполняет поиск и может использовать голосовой сценарий без ввода конфигурации. Ни один общий
секрет нельзя извлечь из release-клиента, а дорогие публичные операции ограничены и наблюдаемы.

## Приоритетный маршрут

### RM-007 — Локальный пользовательский контур и данные

**Зачем:** дать пользователю полезный личный опыт до входа в аккаунт и подготовить данные к
безопасной синхронизации.

**RockMobile и RockCast:**

- локальные избранное, история, счётчик запусков и последнее воспроизведение;
- одинаковое использование stable station ID из RM-004;
- экран управления избранным/историей и понятное поведение при удалённой или заменённой станции;
- экспортируемая внутренняя модель, не завязанная на URL и не требующая RockServer.

**RockServer:**

- зафиксировать будущие DTO и правила слияния данных, но не включать синхронизацию до RM-011;
- гарантировать, что активный каталог и replacement/tombstone semantics пригодны для избранного.

**Готово, когда:** оба клиента работают с локальными личными данными офлайн, а перенос этих
данных в аккаунт не потребует смены идентификаторов станций.

### RM-011 — Регистрация, вход и привязка устройств

**Зачем:** создать минимальный, безопасный интернет-контур для бета-пользователей. Нынешняя
AI-поисковая часть RM-011 переносится после этого этапа; она не нужна для первой проверки
регистрации и управления.

**RockServer:**

- версии `/v1` для регистрации, входа, refresh/logout, получения профиля и удаления сессии;
- хранение паролей только в виде современного password hash; rate limit и нейтральные ответы для
  защиты от перебора и перечисления пользователей;
- короткоживущий access token и отзыв/ротация refresh token; журналирование только безопасных
  событий с request ID;
- сущности `user`, `session`, `device` и миграции PostgreSQL;
- регистрация устройства с отображаемым именем, списком устройств и возможностью отозвать доступ;
- OpenAPI, детерминированные тесты и ошибочные сценарии без реальных почтовых/SMS-провайдеров.

**RockMobile и RockCast:**

- регистрация/вход/выход, безопасное локальное хранение токенов средствами платформы;
- анонимное продолжение работы при отмене входа или недоступности сервера;
- экран списка своих устройств и явное удаление привязки.

**ESP32 (после появления платы):**

- привязка через одноразовый QR-код или короткий код, созданный уже вошедшим пользователем;
- отдельный ограниченный device token; прошивка не получает пароль или основной refresh token.

**Готово, когда:** внешний пользователь создаёт аккаунт, входит с RockMobile или RockCast,
видит и отзывает устройство, а клиент остаётся пригодным для радио без входа.

### RM-012 — Синхронизация, права и персональное управление

**Зачем:** сделать один аккаунт полезным на нескольких клиентах и проверить реальное удалённое
управление до ESP32.

**RockServer:**

- синхронизация избранного, истории и пользовательских предпочтений с правилами конфликтов;
- пользовательские права: владелец аккаунта управляет только своими устройствами;
- команды устройства: воспроизвести station ID, pause/resume, stop, громкость и текущее состояние;
- идемпотентные команды, acknowledgement и явные состояния offline/unsupported;
- аудит только факта команды и результата, без токенов и личных данных.

**RockMobile и RockCast:**

- включаемая синхронизация, статус последней синхронизации и понятный offline queue/ошибка;
- экран управления своими устройствами; команды не должны ломать локальное воспроизведение;
- privacy controls: отключение синхронизации и удаление локальной учётной записи.

**ESP32 (после появления платы):**

- получает только разрешённые команды и отправляет состояние;
- минимальная прошивка без каталога, AI и учётных секретов; интерфейс — кнопки/энкодер/экран
  согласно реальному железу.

**Готово, когда:** один пользователь входит на двух клиентах, видит одинаковое избранное,
управляет только своими устройствами и может отключиться без потери офлайн-радио.

## Удобное развёртывание RockServer

### Рекомендованный первый production-вариант

Один небольшой VPS и собственный домен. На VPS запускается Docker Compose из трёх сервисов:
`caddy`, `rockserver`, `postgres`. В интернет открыты только 80/443 у Caddy; PostgreSQL остаётся
во внутренней Docker-сети и не имеет публичного порта. Caddy выдаёт и продлевает HTTPS-сертификаты
для домена, а RockServer получает трафик только от reverse proxy. Docker рекомендует Compose как
простой путь для single-server production и отдельный production override; Caddy автоматически
включает HTTPS при настроенном доменном имени. [Docker Docs](https://docs.docker.com/compose/how-tos/production/)
[Caddy Docs](https://caddyserver.com/docs/quick-starts/reverse-proxy)

### Процесс выпуска

1. CI запускает тесты, проверки формата и сборку неизменяемого container image по commit SHA.
2. После ручного подтверждения release image публикуется в приватный registry.
3. VPS получает конкретный image tag, выполняет backup PostgreSQL, migration/preflight и
   `docker compose up -d`.
4. Deployment считается успешным только после `/health/ready` через публичный HTTPS-домен.
5. Rollback — возврат на предыдущий image tag и проверенный backup/совместимая миграция.

На старте это лучше Kubernetes: меньше движущихся частей, понятный rollback и один способ
запуска для staging и production. Позже можно добавить отдельный staging VPS, но не до первой
пользовательской беты.

### Обязательные эксплуатационные меры до публичной регистрации

- отдельные production secrets вне git и `.env` вне репозитория;
- ежедневный зашифрованный PostgreSQL backup вне VPS и проверка восстановления по расписанию;
- health/readiness, структурированные логи, uptime-monitor и оповещение о недоступности;
- firewall, SSH-ключи, отключённый password login, регулярные обновления ОС;
- политика удаления аккаунта, история обработки персональных данных и ограничение сроков хранения.

`pg_dump` подходит для переносимого логического backup, который можно восстановить на другой
совместимой машине через `pg_restore`. [PostgreSQL Docs](https://www.postgresql.org/docs/17/app-pgdump.html)

## Очерёдность запуска

1. Реализовать MVP-001 и проверить анонимный публичный сценарий без токена.
2. Закрыть окружение Android API-36 и подтвердить RM-004-I на устройстве/offline.
3. Реализовать RM-007 локально в обоих клиентах.
4. Подготовить deployment foundation и staging-домен без публичной регистрации.
5. Реализовать RM-011, провести security review и закрытую регистрацию небольшой группы.
6. Реализовать RM-012 и проверить синхронизацию/управление с RockCast и RockMobile.
7. После получения платы создать ESP32-клиент, используя уже проверенные device pairing и command API.

## Вне первого интернет-цикла

- голосовой/advanced AI search, Chromecast, Android Auto, relay и smart-home интеграции;
- поиск RockServer в локальной сети;
- кластеризация, Kubernetes и multi-region deployment.
