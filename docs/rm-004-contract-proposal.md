# RM-004-A — Shared station catalog contract proposal

Status: **APPROVED / NOT IMPLEMENTED**  
Date: 2026-08-21  
Approved: 2026-08-21  
Scope: architecture and contract design only

This document is the approved RM-004-A acceptance-gate contract. It records verified behavior in
RockServer, RockCast, and RockMobile and fixes the canonical v1 contract and migration rules.
Approval records the design decision only: RM-004-B and later implementation remain not started and
require separate explicit execution.

## Goals and boundaries

### APPROVED DECISION

- One separately released baseline catalog supplies the same station and stream identities to
  RockServer, RockCast, and RockMobile.
- Each consumer vendors an immutable, checksum-verified snapshot. Clean builds and normal runtime
  fallback never require a sibling checkout, a live RockServer, or network access.
- The future authoring repository owns curated baseline identity and descriptive metadata.
  RockServer owns discovery-provider records and operational enrichment.
- RockServer continues to be the online search, voice, ranking, health, probe, embedding, and
  provider-import service. It is not made the only source required for basic client playback.
- RockMobile also ships a derived extended offline snapshot exported from RockServer PostgreSQL,
  targeting all eligible stations (currently approximately 16,000) for local name and genre/tag
  search. This export is separate from, and does not redefine, the curated canonical baseline.

### Non-goals

- No station data conversion, repository creation, validator, adapter, snapshot synchronizer,
  database migration, HTTP change, client change, or live import is part of RM-004-A.
- Canonical v1 does not model user favourites, history, ranking scores, probe results, credentials,
  provider popularity, or personalization.
- Canonical v1 does not automatically merge a baseline station with a Radio Browser row merely
  because names or URLs look similar.
- The proposal does not make generated IDs authoritative. The first ID set requires human review.

## Verified current behavior

### RockServer

**VERIFIED CURRENT BEHAVIOR**

- `search::Station` has `id`, `name`, one selected `stream_url`, nullable `homepage_url`, `tags`,
  nullable `language`, nullable `country_code`, nullable `codec`, nullable `bitrate_kbps`, and
  `health`. `RankedStation` adds `score` and `reason`.
- The in-memory catalog currently contains seven hard-coded single-stream stations. PostgreSQL is
  selected when `DATABASE_URL` exists; otherwise in-memory search is used.
- PostgreSQL separates `stations` from `station_streams`. `stations.id` is a `varchar(128)` primary
  key. Streams have a database-generated bigint primary key, station foreign key, URL, codec,
  bitrate, health, `is_primary`, timestamps, provider ownership, and probe columns.
- The database permits several streams per station and enforces at most one primary stream with a
  partial unique index. It does not enforce at least one stream or exactly one primary stream.
- Migration 0003 removed global stream-URL uniqueness. Provider identities are unique as
  `(stations.source, source_station_id)` and `(station_streams.source, source_stream_id)`.
- Built-in rows use source `builtin`. Radio Browser rows use `radio_browser`; their upstream UUID is
  `source_station_id`, RockServer ID is `rb-<uuid>`, and the current single stream reuses the UUID as
  `source_stream_id`.
- `CatalogImportProvider` fetches normalized pages. `CatalogImporter` owns run orchestration and
  verifies provider ownership. `CatalogImportStore` owns run persistence and page upsert. The
  current `ImportedStation` carries exactly one stream.
- `PostgresImportStore` upserts only on source identity, updates a Radio Browser station and its
  stream in place, and retains records missing from later provider pages. It currently marks every
  imported stream healthy. No import delete/disable sweep exists.
- Search selects one stream by `is_primary DESC, station_streams.id ASC`, excludes a selected stream
  whose health is `degraded`, and returns no stream identity in the public DTO.
- Probe state (`health`, `last_probe_at`, `last_probe_error`) is updated by stream URL. Embeddings are
  keyed by station plus model/version and generated by a separate backfill over `searchable_text`.
  Import/startup/search do not generate embeddings.
- `POST /v1/search`, JSON voice-command responses, and WebSocket voice-result events share the
  `StationResult` shape: `id`, `name`, `stream_url`, nullable `homepage_url`, `tags`, nullable
  `language`, nullable `country_code`, nullable `codec`, nullable `bitrate_kbps`, `score`, `reason`,
  and `health`. The public response exposes only the chosen stream.
- OpenAPI declares `StationResult.additionalProperties: false`; it does not expose favicon, aliases,
  provider metadata, catalog version, stream ID, or multiple streams.

### RockCast

**VERIFIED CURRENT BEHAVIOR**

- `stations::Station` has `name`, `url`, comma-separated `tags`, free-text `country`, `bitrate: u32`,
  and `codec`. It has no station ID, stream ID, language, homepage, favicon, health, or provider.
- `stations.txt` format is `name | url | tags | bitrate | codec | country`. Name and HTTP(S) URL are
  required. Missing/invalid bitrate defaults to 128, codec defaults to `mp3`, and country/tags
  default to empty strings. Extra fields are ignored.
- The current file has 41 valid records, 41 unique case-folded URLs after trimming trailing `/`, no
  duplicate names, and no duplicate URLs. Codecs are `aac`/`mp3`; countries are Canada, Germany,
  Russia, Switzerland, UK, and USA.
- Catalog lookup precedence is `ROCKCAST_STATIONS`, executable directory, current directory, then
  app-data `stations.txt`. If none exists, the embedded file is used and an editable app-data copy
  is attempted.
- RockCast orders metal-like tags first, then HTTPS before HTTP, then case-folded name. Radio Browser
  enrichment prepends fetched rows, deduplicates by normalized URL, orders, and truncates to 120.
  If enrichment fails, the ordered local catalog remains available.
- When enabled, RockServer search can replace the displayed catalog; empty/error responses fall
  through to Radio Browser enrichment and ultimately the local list.
- RockServer and voice DTOs discard server station ID, homepage, language, health, score/reason, and
  any stream identity when converting to the local `Station`.
- Playback uses the station URL. Persisted selection is `station_url`; `last_played_station` stores a
  full URL-based station snapshot. Restore, removal of a failed stream, and voice fallback compare
  URLs. There is no favourites/history feature or stable station identity today.

### RockMobile

**VERIFIED CURRENT BEHAVIOR**

- Domain `Station` has `id`, `name`, `streamUrl`, `tags`, nullable `country`, nullable `language`,
  nullable `codec`, nullable `bitrateKbps`, nullable `homepageUrl`, and nullable `faviconUrl`.
- RockServer DTO parsing requires non-empty `id`, `name`, and HTTP(S) `stream_url`; it accepts the
  optional domain fields. The current public server contract does not actually return favicon.
- Bundled fallback parses the unmodified RockCast TXT shape. Each bundled ID is computed as
  `rockcast-` plus the first 16 lowercase hex characters of SHA-256 over the lowercased stream URL
  with trailing `/` removed. A URL change therefore changes identity.
- The bundled data rows are byte-for-byte equal to RockCast after comments are removed: 41 records
  and 41 unique derived IDs. The complete files have different hashes because their comments differ.
- `StationRepository` is RockServer-first. Network, timeout, non-success HTTP, malformed JSON, and
  empty remote results use the bundled catalog; coroutine cancellation is rethrown; failure of both
  sources is fatal.
- Filtering is client-side by name substring and exact case-insensitive tag/country/language.
  Playback uses `streamUrl`, uses station ID as Media3 `mediaId`, and locates queue entries by ID.
- There is no favourites/history implementation yet (RM-007 is future work). The existing
  `UnavailableVoiceStationStore` does persist up to 100 unavailable voice station IDs, so identity
  migration already matters before favourites/history exists.

## Proposed canonical v1 structure

**APPROVED DECISION**

The normative proposed schema is
[`rm-004-stations-v1.schema.proposed.json`](rm-004-stations-v1.schema.proposed.json), and the aligned
example is [`rm-004-stations-v1.example.json`](rm-004-stations-v1.example.json).

```text
envelope
  schemaVersion: 1
  catalogVersion: YYYY.MM.N
  stations: ordered active station records
    id, name, aliases[], legacyIds[], tags[]
    countryCode, language, homepageUrl, faviconUrl
    streams[]: id, url, codec, bitrateKbps, primary
  tombstones[]: id, reason, replacementIds[]
```

### Required fields, nullability, and allowed values

| Field | Required | Nullable | Rules |
|---|---:|---:|---|
| `schemaVersion` | yes | no | Integer constant `1` |
| `catalogVersion` | yes | no | `YYYY.MM.N`; `N >= 1`; immutable once published |
| `stations` | yes | no | At least one active station; reviewed array order is baseline display order |
| `tombstones` | yes | no | May be empty; retained across releases |
| `station.id` | yes | no | 1–96 lowercase ASCII letters/digits separated by single hyphens; globally unique and never reused |
| `station.name` | yes | no | Trimmed, non-empty, Unicode NFC, maximum 200 characters |
| `station.aliases` | yes | no | 0–32 trimmed unique NFC display/search names; excludes the current `name`; deterministically sorted |
| `station.legacyIds` | yes | no | 0–32 globally unique `namespace:value` identifiers; migration-only; deterministically sorted |
| `station.tags` | yes | no | 0–32 trimmed unique NFC lowercase values, each at most 64 characters; deterministically sorted |
| `station.countryCode` | yes | yes | `null` or an assigned ISO 3166-1 alpha-2 uppercase code |
| `station.language` | yes | yes | `null`, ISO 639-1 lowercase alpha-2 when available, otherwise ISO 639-2/T alpha-3 |
| `station.homepageUrl` | yes | yes | `null` or canonical HTTP(S) URL without credentials or fragment |
| `station.faviconUrl` | yes | yes | `null` or canonical direct HTTP(S) image URL without credentials or fragment |
| `station.streams` | yes | no | At least one; unique IDs; globally unique normalized URLs; exactly one `primary: true` |
| `stream.id` | yes | no | 1–31 lowercase ASCII letters/digits/hyphens; unique within station; full identity is `(station.id, stream.id)` |
| `stream.url` | yes | no | Canonical absolute HTTP(S), max 2048 characters, no credentials or fragment; HTTPS preferred but HTTP accepted |
| `stream.codec` | yes | yes | `null` or lowercase token matching `[a-z0-9][a-z0-9.+-]*`, max 32; known examples include `mp3`, `aac`, `aacp`, `opus`, `vorbis`, `ogg`, `flac` |
| `stream.bitrateKbps` | yes | yes | `null` or integer 1–2000 |
| `stream.primary` | yes | no | Boolean; exactly one true per station |
| `tombstone.id` | yes | no | A retired canonical station ID; never active in the same release |
| `tombstone.reason` | yes | no | `removed`, `merged`, or `split` |
| `tombstone.replacementIds` | yes | no | Empty for removed, exactly one for merged, at least two for split |

JSON Schema regexes can check code shape but not membership in current ISO registries. They also
cannot enforce uniqueness by a nested key, canonical URL equivalence, Unicode normalization,
sorting, replacement-graph acyclicity, or cross-array references. RM-004-B's separate deterministic
validator must enforce all of those rules. Draft 2020-12 `contains`/`minContains`/`maxContains`
does express exactly one primary stream; the external validator must repeat the check for clear
errors and defense in depth.

Known properties are required even when their value is absent, using `null` or an empty array. This
prevents consumers from giving different meanings to missing versus unknown values. Unknown
optional properties are intentionally accepted at envelope, station, stream, and tombstone levels;
schema-v1 consumers must ignore them. Authoring remains strict: a producer-side allowlist should
reject accidental misspellings before release. Adding an optional field with unchanged semantics is
v1-compatible; making a field required or reinterpreting it requires schema v2.

## Identity policy

### APPROVED DECISION

- Existing RockCast rows receive candidate slugs from normalized names only as a review aid. No
  generated candidate becomes canonical until every row and collision report is approved by a
  human in RM-004-C.
- A new station ID is chosen by an author after checking active IDs, tombstones, aliases, existing
  providers, and likely brand continuity. Prefer a durable brand/service slug rather than location,
  codec, bitrate, or URL details likely to change.
- A migrated single stream receives `id: main`. New secondary IDs describe stable roles such as
  `backup`, `low-bandwidth`, or `regional-eu`; they do not encode a URL hash. Codec-specific IDs are
  allowed only when codec is the durable role, not merely today's transport.
- Station IDs are globally unique forever. Stream IDs are unique within a station forever. Retired
  values are reserved and cannot be reassigned to unrelated entities.
- The proposed 96/31 length limits make RockServer `source_stream_id = <station.id>:<stream.id>` fit
  its current 128-character column exactly, including the separator.

### Lifecycle rules

| Change | Required identity behavior |
|---|---|
| Stream URL changes | Keep station and stream ID when the new endpoint is the operational successor. Reset RockServer health/probe state for that stream; do not change client identity. |
| Station rename/rebrand | Keep station ID. Update `name`; add the old user-recognizable name to `aliases` when useful. |
| Display alias | Add to `aliases`; aliases never resolve as persistent IDs. |
| Add/remove secondary stream | Keep station ID and unaffected stream IDs. Add a reviewed new stream ID; tombstone removal is not needed for stream IDs in v1, but the ID remains reserved. |
| Merge duplicate stations | Select the continuity survivor; move useful aliases, legacy IDs, and nonduplicate streams; tombstone the losing canonical ID with `reason: merged` and one replacement ID. |
| Split one station | Keep the old ID only for the clearest continuity successor and issue new IDs to the others. If no single successor is correct, tombstone with `reason: split` and multiple replacements; persisted user state must not be silently assigned. |
| Remove station | Remove it from `stations`, retain a `removed` tombstone with no replacement, and never reuse its ID. |
| Collision | Fail validation and release. Do not suffix or overwrite automatically after review has frozen an ID. Resolve explicitly and rerun the full mapping review. |

Replacement targets must be active, not self-referential, and form an acyclic graph after resolving
older tombstones. Consumers may follow `merged` chains to an active ID. A `split` is deliberately
ambiguous and requires product-specific user choice for favourites/history.

## Baseline authoring versus RockServer enrichment

### APPROVED DECISION

| Data | Owner | Rule |
|---|---|---|
| IDs, name, aliases, tags, country, language | Baseline authoring | Reviewed, versioned, immutable per release |
| Homepage and favicon | Baseline authoring | Curated nullable URLs; consumers may cache/display but must tolerate network failure |
| Stream URL, codec, bitrate, primary role | Baseline authoring | Versioned transport declaration, not a health assertion |
| Health, probe result/error/time | RockServer | Never copied back into baseline automatically |
| Embedding vector/model/version/input freshness | RockServer | Derived; never stored in canonical JSON |
| Radio Browser UUID, source, votes, clicks, last-check, import run | RockServer/provider | Provider-owned; never overwrites baseline ownership |
| Search score/reason and voice selection | RockServer request | Ephemeral response fields |
| Station/stream created/updated timestamps | RockServer database | Operational audit only |
| Release timestamp | Release system | Stored in immutable release/tag metadata, not repeated in each catalog record |

If baseline metadata changes `searchable_text`, RockServer invalidates that station's derived
embeddings and lets the existing controlled workflow rebuild them; import does not call an embedding
provider. If a stream URL changes under the same stream ID, RockServer resets that stream's health
to `unknown` and clears probe time/error. Metadata-only updates preserve existing probe state.

## Versioning, releases, and offline policy

### APPROVED DECISION

- `schemaVersion` defines interpretation. Consumers in this rollout accept exactly `1`; an unknown
  value is rejected and the prior pinned snapshot remains usable.
- `catalogVersion` identifies data bytes, not schema semantics. Format is calendar sequence
  `YYYY.MM.N`; every different canonical byte set gets a new value.
- A published catalog version is immutable. Corrections publish a later version; tags/releases are
  never rewritten.
- A release contains the canonical JSON, its schema, and a SHA-256 checksum manifest. The checksum
  covers the exact UTF-8 canonical JSON bytes after deterministic formatting.
- Each consumer pins both catalog version and checksum and vendors the JSON. Snapshot updates are an
  explicit reviewed action. Cargo/Gradle builds and application startup never fetch a catalog.
- Within schema v1, consumers ignore unknown optional properties but reject missing/invalid known
  required properties and all semantic-invariant failures. Producers cannot add a required field or
  reinterpret an existing field without schema v2.
- Rollback means pinning the previous immutable version/checksum. The prior vendored bytes remain in
  version control, so rollback is possible without the catalog host or RockServer.

## Extended RockMobile offline catalog

### APPROVED ADDENDUM

- RockMobile ships two independently recoverable local layers: the curated canonical baseline and a
  larger derived snapshot exported from RockServer PostgreSQL.
- The extended snapshot targets every station that satisfies explicit active/playable eligibility
  rules; the current expected size is approximately 16,000 stations.
- It is available on first launch without RockServer and supports indexed local search by normalized
  station name and genre/tags.
- The released mobile artifact is a prebuilt Room/SQLite database (or byte-equivalent SQLite
  artifact accepted by Room), not a raw PostgreSQL dump and not a full in-memory JSON catalog.
- The export contains stable station/provider identity, display name, normalized genres/tags,
  country/language, primary playable stream, homepage/favicon URL, and optional codec/bitrate needed
  by the client.
- Health history, probe results/errors/timestamps, embeddings, import-run bookkeeping, credentials,
  provider-private data, and other server-operational fields are excluded.
- Favicon/logo bytes are not bundled for all stations; URLs are stored and images are cached on
  demand.
- Export eligibility, deduplication, ordering, normalization, schema/version, checksum, and rollback
  are deterministic and tested. Generation and client adoption are explicit release actions.
- A missing, corrupt, incompatible, or checksum-invalid extended snapshot never disables basic
  radio: RockMobile falls back to the independently bundled curated baseline.
- Online RockServer results remain primary when available. AI, semantic search, ranking, voice,
  personalization, live health, and provider enrichment remain RockServer capabilities.
- The extended snapshot is derived product data and never becomes the authoring source of truth for
  the canonical baseline.

## Exact legacy migration

### RockCast `stations.txt`

**APPROVED DECISION**

RM-004-C performs a deterministic conversion of all 41 current records in original data order:

1. Parse with the current six-field meaning; report rather than silently accept malformed rows.
2. Copy `name`; split tags on comma, trim, NFC-normalize, lowercase, deduplicate, and sort.
3. Copy URL into one `main` stream and copy the explicitly present bitrate/codec after validation.
4. Map current country names exactly: `USA→US`, `UK→GB`, `Germany→DE`, `Russia→RU`, `Canada→CA`,
   `Switzerland→CH`. Any other value is an explicit review item, not an inferred code.
5. Set `language`, `homepageUrl`, and `faviconUrl` to `null`; do not infer them from country, name,
   domain, or network checks.
6. Generate a candidate station slug from the name and a candidate `main` stream ID, then require
   row-by-row human approval before freezing them.
7. Compute the existing RockMobile URL ID with its exact current algorithm and store it as
   `legacyIds: ["rockmobile:<old-id>"]`.
8. Preserve the original 41-row array order so RockMobile's initial bundled ordering does not
   change. RockCast may continue applying its current tag/HTTPS/name ordering after load.

The conversion report must show input/output/rejected counts, duplicate normalized URLs, duplicate
names, candidate-ID collisions, country mappings, and every value changed by normalization. Current
inventory predicts 41 accepted, zero duplicate names, and zero duplicate normalized URLs, but the
converter must prove this from the exact pinned input rather than trust this proposal.

RockCast's override precedence, editable app-data copy behavior, local-first immediate display,
Radio Browser enrichment, URL dedupe, current ordering, 120-row enrichment cap, playback, relay,
Cast behavior, and offline startup remain unchanged during migration. A transition TXT adapter may
remain for one explicitly dated release, as already planned; RM-004-A implements none of it.

### RockMobile URL-derived IDs

**APPROVED DECISION**

- The first canonical snapshot carries all 41 exact current bundled IDs as namespaced `legacyIds`.
- On the future client migration, build a one-to-one map from raw legacy value
  `rockcast-<16 hex>` to canonical station ID. Translate the existing unavailable-voice ID set before
  normal catalog use, write canonical IDs atomically, retain unmatched legacy values for one
  transition release, and make the migration idempotent.
- The same resolver becomes mandatory input to RM-007 favourites/history. New persisted user state
  stores only canonical station IDs; it must never store URL-derived identity.
- `merged` tombstones may redirect stored IDs automatically. `split` tombstones may not; they require
  user selection or a deliberately documented product policy.
- Remote and bundled entries converge on the same canonical station IDs after RockServer and the
  mobile snapshot both adopt the release. Until then, existing remote IDs remain unchanged.

## RockServer mapping and coexistence

### APPROVED DECISION

| Canonical value | Future RockServer mapping |
|---|---|
| `station.id` | `stations.id` unchanged and `source_station_id` unchanged |
| Baseline ownership | `stations.source = 'rockcatalog'`; stream source also `rockcatalog` |
| `(station.id, stream.id)` | `source_stream_id = '<station.id>:<stream.id>'`; DB bigint stream ID remains internal |
| name/homepage/tags/language/country | Existing station columns; aliases require internal persistence/search support; favicon may be persisted internally but is not added to current API |
| stream URL/codec/bitrate/primary | Existing stream columns, one row per canonical stream |
| legacy IDs/tombstones | Import/migration lifecycle metadata; never emitted in current search/voice DTOs without separate approval |

Import must preflight the complete snapshot before starting writes. It rejects canonical IDs that
collide with an existing different source, duplicate source identities, invalid tombstone graphs, or
ambiguous primary streams. A page/run is source-bound as today.

- Insert: create provider-owned station and all streams. New streams start with health `unknown`.
- Update: match by canonical source identities, update baseline-owned columns, preserve health/probe
  state unless URL changed, and invalidate embeddings only when their input document changed.
- Stream removal: retire only the missing `rockcatalog` stream after the complete release has
  validated; never touch another source's stream.
- Station removal/tombstone: soft-retire only the `rockcatalog` row from search while retaining
  identity/audit data for rollback. The exact internal soft-retirement column/table is an RM-004-D
  migration design detail, not part of the canonical JSON contract.
- Failed/incomplete import: expose a failed import run and leave the previously active release
  intact. Activation occurs only after the whole snapshot succeeds.
- Rollback: re-import/reactivate the prior pinned version; do not mutate published catalog bytes.
- Radio Browser: retain existing `radio_browser` ownership, UUID IDs, importer behavior, and missing-
  row retention. Cross-provider duplicates may coexist; no automatic ownership transfer or merge is
  allowed. A future entity-resolution task may address duplicate search results.

The current `ImportedStation`/`PostgresImportStore` single-stream shape is insufficient for this
mapping. Any extension belongs to RM-004-D after approval, with deterministic fakes and tests; this
proposal does not modify it.

## Behavior that must remain unchanged

### APPROVED DECISION

- RockServer keeps current public paths, authentication, request validation, error shape, normalized
  query shape, `StationResult` fields/nullability, single selected `stream_url`, health values,
  ranking, score/reason, exclusions, limits, and voice `selected_station` semantics.
- OpenAPI remains the public source of truth. Canonical JSON camelCase names do not leak into current
  snake_case HTTP DTOs. Favicon, aliases, catalog version, stream ID, and secondary streams are not
  added to current API during RM-004-D without a separate reviewed API revision.
- Existing database provider ownership and unique source identities remain. Radio Browser import,
  run history, health/probe ownership, embedding provenance, readiness, and background separation
  remain isolated from request handling.
- RockCast still starts and plays offline, honors local override precedence, preserves its current
  ordering/dedupe/enrichment/fallback behavior, and sends the chosen URL to existing playback.
- RockMobile remains RockServer-first with bundled fallback for network/HTTP/malformed/empty remote
  outcomes, does not turn playback errors into catalog fallback, keeps current filters, and plays the
  primary stream through Media3 while offline.
- No consumer build or startup performs an implicit catalog download.

## Staged rollout and rollback

### APPROVED DECISION

1. **RM-004-A gate:** approve schema, identity, ownership, migration, and rollback decisions.
2. **RM-004-B/C:** create the separate repository/tooling, convert the exact 41-row input, review all
   generated IDs, and publish a release candidate. No consumer changes yet.
3. **RockServer shadow stage:** validate/import the candidate under `rockcatalog` without replacing
   Radio Browser ownership; compare counts and sample mappings. Activation is atomic and reversible.
4. **RockMobile stage:** ship pinned JSON plus legacy-ID migration while retaining the previous TXT
   snapshot in version control. Verify server-off playback before enabling the new loader by default.
5. **RockCast stage:** ship pinned JSON and a time-bounded TXT transition adapter while preserving
   overrides and offline behavior.
6. **Synchronization stage:** automate explicit snapshot updates/checksum checks; never build-time
   downloads.
7. **Cross-project gate:** compare IDs/streams and exercise rename, URL change, secondary stream,
   tombstone, duplicate-provider, outage, and rollback scenarios before cleanup.

At any stage, rollback pins the previous catalog release and reverts only that consumer's explicit
snapshot/import activation. Radio Browser rows and server-owned enrichment are not deleted. Legacy
TXT support is removed only after both clients have shipped and verified the JSON path.

## Risks

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| Human-generated ID churn breaks persisted state | High | Medium | Full 41-row review, immutable tombstones, legacy mappings, no auto-freeze |
| URL change loses RockMobile availability/future favourites history | High | High without migration | Namespaced legacy IDs and idempotent canonical-ID migration before RM-007 |
| Cross-provider duplicate stations appear in RockServer results | Medium | High | Preserve ownership, reject automatic merges, add explicit later entity-resolution work |
| Import partially activates a catalog | High | Medium | Whole-snapshot validation, transactional/staged activation, failed run leaves prior release active |
| Baseline update overwrites probe/health/embedding ownership | High | Medium | Field ownership matrix, preserve/reset rules, targeted invalidation tests |
| Tombstone or split redirects user state incorrectly | High | Low–Medium | Acyclic validation; auto-follow merge only; never auto-resolve split |
| Forward-compatible unknown field hides a typo | Medium | Medium | Permissive consumer schema plus strict producer allowlist and deterministic formatting |
| Country/language regex accepts unassigned codes | Medium | Medium | Offline pinned ISO registry validation; no network checks |
| Multiple streams change current playback selection | High | Medium | Exactly one primary; clients use primary only in initial rollout; preserve public single-stream DTO |
| Favicon becomes a hidden runtime dependency | Low | Medium | Nullable field, graceful failure/cache policy, never required for playback |
| Soft-retired rows leak into search | High | Low–Medium | Provider-scoped active filter and deletion/rollback integration tests in RM-004-D |
| Canonical array order changes RockMobile UI unexpectedly | Medium | Medium | Preserve reviewed legacy row order in first release and test it explicitly |
| HTTP-only legacy streams remain security/reliability liabilities | Medium | High | Permit for compatibility, prefer HTTPS for new data, track later curated replacement without changing identity |
