# Дорожная карта модернизации голосового поиска и векторного ранжирования (RockServer / RockCast)

Документ фиксирует декомпозированный план задач по устранению архитектурных, алгоритмических и операционных недочётов поисково-голосового конвейера на основе технического аудита от 29.08.2026.

Задачи структурированы для изолированного поручения автономным агентам (Codex, Antigravity, Claude и др.).

---

## Принципы и правила реализации для агентов

1. **Границы репозиториев (см. `AGENTS.md`):**
   - Задачи `SRCH-*` выполняются строго в репозитории `rockserver`.
   - Задача `RC-VOICE-*` выполняется строго в репозитории `rockcast`.
   - Серверные и клиентские изменения не объединяются в один коммит или PR.
2. **Обязательные проверки перед сдачей любой задачи в `rockserver`:**
   ```text
   cargo fmt --check
   cargo clippy --all-targets --all-features -- -D warnings
   cargo test
   ```
3. **Обновление документации:**
   Каждая выполненная задача обязана обновить `docs/status.md` и `docs/tasks.md` перед завершением.
4. **Безопасность и отсутствие внешних вызовов:**
   Юнит-тесты не должны вызывать реальные внешние API (Yandex Cloud) или сеть. Для тестов используются детерминированные моки и фейки.

## Фаза 1. Разблокировка рантайма и исправление ретривера (P0)

### Задача SRCH-001: Неблокирующий инференс ONNX и пул сессий
* **Проблема:** В `src/providers/onnx_e5.rs` метод `embed` синхронно вызывает токенизацию и `session.run()` внутри async-функции, блокируя воркер-тред Tokio на 100–150 мс. Одиночный `Mutex<Session>` сериализует все параллельные запросы в очередь (concurrency = 1), вызывая деградацию параллельных голосовых WebSocket-сессий.
* **Цель:** Изолировать CPU-интенсивный инференс от Tokio рантайма и поддержать параллельное исполнение.
* **Область изменений:** `src/providers/onnx_e5.rs`.
* **Изменения:**
  1. Обернуть выполнение токенизации и инференса в `tokio::task::spawn_blocking`.
  2. Реализовать пул сессий ONNX (или семафор/очередь с пулом из $N$ инстансов `Session`, где $N = \min(\text{num\_cpus}, 4)$).
  3. Устранить глобальный мьютекс, заменив его взятием свободной сессии из пула на время вызова.
* **Acceptance criteria:**
  - Ни один вызов `ort::Session::run` или `Tokenizer::encode` не выполняется на треде планировщика Tokio.
  - Параллельные вызовы `embed` на многоядерной системе выполняются конкурентно без сериализации в один поток.
* **Тесты:** Нагрузочный/многопоточный юнит-тест в `src/providers/onnx_e5.rs` с конкурентными запросами к моку/провайдеру.

### Задача SRCH-002: Истинный векторный ANN-ретривер через HNSW в PostgreSQL
* **Проблема:** В `src/persistence/postgres.rs` (`SEARCH_SQL`) HNSW-индекс из `migrations/0005_...sql` никогда не задействуется pgvector, так как отсутствует `ORDER BY embedding <=> ... LIMIT k`. Векторы подтягиваются через `LEFT JOIN` только к 200 кандидатам, уже отобранным по тегам/FTS/триграммам. Семантический поиск не работает как ретривер — recall ограничен чистой лексикой. Выражение индекса `((embedding::vector(384)) vector_cosine_ops)` не совпадает с типом в запросе без явного приведения.
* **Цель:** Сделать векторный поиск полноценной независимой веткой выборки кандидатов с использованием HNSW-индекса.
* **Область изменений:** `src/persistence/postgres.rs`, при необходимости новая миграция для уточнения индекса.
* **Изменения:**
  1. В `SEARCH_SQL` добавить отдельную CTE `semantic_candidate_ids`:
     ```sql
     semantic_candidate_ids AS (
         SELECT se.station_id AS id
         FROM station_embeddings se
         WHERE se.model = $8 AND se.version = $9 AND se.dimension = $10
           AND $7::text IS NOT NULL
         ORDER BY (se.embedding::vector(384)) <=> ($7::text)::vector(384)
         LIMIT 100
     )
     ```
  2. Включить `semantic_candidate_ids` в общий `candidate_match_ids` через `UNION`.
  3. Убедиться, что типы и оператор точно соответствуют выражению HNSW-индекса, проверяя план выполнения (`EXPLAIN`).
* **Acceptance criteria:**
  - Запрос типа «поставь что-нибудь для бодрой тренировки» возвращает станцию с подходящим описанием/эмбеддингом, даже если в названии и тегах нет ни одного общего слова или триграммы.
  - В плане `EXPLAIN` при наличии эмбеддинга виден `Index Scan using station_embeddings_e5_small_hnsw_cosine_idx`.
* **Тесты:** Тесты в `tests/postgres_integration.rs` на нахождение кандидатов исключительно по семантическому вектору при нулевом лексическом совпадении.

### Задача SRCH-003: Корректный порядок префильтрации в SQL
* **Проблема:** В `src/persistence/postgres.rs`:
  1. CTE `prefiltered` применяет `LIMIT GREATEST($6 * 20, 200)` **до** проверки `health <> 'degraded'` и наличия живого потока. Мёртвые станции вытесняют живые из топ-200.
  2. `prefilter_score` учитывает только совпадения тегов и FTS (`ts_rank_cd`). Кандидаты из триграммной ветки (`trigram_candidate_ids`) получают `0.0` и при лимите сортируются по `s.id ASC`, отсекая релевантные станции с более поздним ID.
* **Цель:** Исключить вытеснение живых станций неработающими и предотвратить потерю триграммных кандидатов.
* **Область изменений:** `src/persistence/postgres.rs` (`SEARCH_SQL`).
* **Изменения:**
  1. Перенести проверку доступности живого потока (`EXISTS (SELECT 1 FROM station_streams ss WHERE ss.station_id = s.id AND ss.retired_at IS NULL AND ss.health <> 'degraded')`) внутрь формирования кандидатов до отсечения по лимиту.
  2. Включить триграммное сходство с названием станции в расчет `prefilter_score`.
* **Acceptance criteria:**
  - Станции без живых стримов не занимают слоты в префильтре.
  - Триграммные кандидаты получают корректный вес в `prefilter_score` и не отсекаются искусственно по `s.id ASC`.
* **Тесты:** Интеграционный тест с добавлением станций с `health = 'degraded'` и станций с высоким триграммным сходством и лексикографически старшим ID.

### Задача SRCH-004: Лексический гейт и мягкий буст для языкового классификатора
* **Проблема:** В `src/search/semantic_filters.rs` 28 прототипов имеют сильный общий шаблон `"Broadcast language: ..."`, из-за чего разница top-1 и top-2 редко превышает 0.04. В `src/search/mod.rs` классификатор вызывается на любой сырой запрос пользователя («включи джаз») и при ложном срабатывании устанавливает жесткий фильтр `intent.language = Some(...)`, вырезающий почти весь каталог.
* **Цель:** Предотвратить ложные срабатывания языкового фильтра и разрушение поисковой выдачи.
* **Область изменений:** `src/search/semantic_filters.rs`, `src/search/mod.rs`.
* **Изменения:**
  1. Добавить обязательный лексический триггер: классификатор вызывается **только** если в тексте запроса присутствуют языковые маркеры (например, "на русском", "english", "по-испански", "deutsch" и т.п.).
  2. Перевести влияние определенного языка из режима жесткого SQL-фильтра (`WHERE s.language = $3`) в режим мягкого буста ранжирования (ranking boost), если язык не был явно запрошен жесткой командой.
  3. В прототипах вычесть общий центроид либо очистить шаблоны от доминирующего шума.
* **Acceptance criteria:**
  - Запрос «включи джаз» никогда не приводит к установке фильтра `language = '...'`.
  - Запрос «включи джаз на французском» корректно распознает французский язык.
* **Тесты:** Юнит-тесты в `src/search/tests.rs` на запросы с языковыми маркерами и без них.

## Фаза 2. Слияние ранжирования и качество интентов (P1)

### Задача SRCH-005: Гибридный скоринг на базе Reciprocal Rank Fusion (RRF)
* **Проблема:** В `postgres.rs` веса 0.70 / 0.30 складывают ненормированный `metadata_score` (до 4.8) с семантическим косинусом (константа $\approx 0.27$). В `ranking.rs` мертвая функция `hybrid_score` не используется в проде.
* **Цель:** Внедрить единый математически корректный механизм слияния списков кандидатов, не зависящий от калибровки шкал.
* **Область изменений:** `src/persistence/postgres.rs`, `src/search/ranking.rs`, `src/search/mod.rs`.
* **Изменения:**
  1. Реализовать слияние результатов лексической ветки (FTS + теги + триграммы) и семантической ветки через алгоритм **RRF (Reciprocal Rank Fusion)**:
     $$RRF\_Score(d) = \sum_{m \in M} \frac{w_m}{k + rank_m(d)},\quad k \approx 60$$
  2. Удалить неиспользуемую функцию `ranking.rs::hybrid_score` либо привести ее к единой формуле с SQL.
  3. Скорректировать логику `MIN_RELEVANCE_SCORE` под новую шкалу RRF.
* **Acceptance criteria:**
  - Станции, находящиеся высоко одновременно в лексическом и векторном списках, получают максимальный ранг.
  - Наличие эмбеддинга больше не дает автоматическую константную надбавку, пробивающую порог отсечения.
* **Тесты:** Тесты на ранжирование в `tests/postgres_integration.rs` и тесты граничных условий в `src/search/ranking.rs`.

### Задача SRCH-006: Очистка запроса от разговорного шума и нормализация текста станций
* **Проблема:** В `src/search/mod.rs` в ONNX E5 уходит сырой пользовательский запрос («включи пожалуйста рок»), где слова «включи», «пожалуйста» вносят шум в 384-мерный вектор. Документ в `searchable_text` конкатенируется как `"Name tags lang country"` («Rock FM rock ru RU»), что далеко от естественного распределения предложений E5.
* **Цель:** Привести векторные представления запроса и документа к оптимальному распределению для модели E5.
* **Область изменений:** `src/search/mod.rs`, `migrations/` (или генерация `searchable_text`), `src/providers/onnx_e5.rs`.
* **Изменения:**
  1. Перед генерацией векторного представления запроса очищать его от типовых командных префиксов («включи», «поставь», «найди», «играй», «play», «please» и т.д.) либо использовать очищенное поле интента.
  2. Привести формат `searchable_text` станции к связному виду: `"Radio station: {name}. Genres: {tags}. Country: {country}, language: {language}."`.
* **Acceptance criteria:**
  - Вектор запроса «включи пожалуйста рок» совпадает или максимально близок к вектору запроса «рок».
  - Повышение релевантности векторного поиска на тестовых фразах.
* **Тесты:** Юнит-тесты на функцию очистки запроса и сравнение косинусных расстояний.

### Задача SRCH-007: Динамическая таксономия жанров в LLM
* **Проблема:** Промпт и JSON Schema для YandexGPT строятся из захардкоженной константы `CANONICAL_TAGS` (44 тега в `src/search/llm.rs`). Добавление жанра в БД через миграцию или админку делает его невидимым для LLM.
* **Цель:** Использовать единый источник правды для таксономии жанров.
* **Область изменений:** `src/search/llm.rs`, `src/search/taxonomy.rs`, `src/search/mod.rs`.
* **Изменения:**
  1. Передавать актуальный список тегов из `GenreTaxonomy` в `LlmQueryParser` при инициализации и обновлении.
  2. Использовать `CANONICAL_TAGS` только как fallback-константу при отсутствии соединения с БД.
* **Acceptance criteria:**
  - При появлении нового тега в таблице `genre_hierarchy` он автоматически появляется в JSON-схеме и системном промпте LLM без перекомпиляции бинарника.
* **Тесты:** Тест генерации JSON-схемы с динамическим списком тегов.

### Задача SRCH-008: Защита и отказоустойчивость LLM-пути
* **Проблема:** При деградации YandexGPT каждый поисковый запрос висит до 4.5 секунд. Нет Circuit Breaker, нет кэша интентов, модель зафиксирована алиасом `/latest` (может измениться без ведома разработчиков), отсутствует rate-limit на `/v1/search`.
* **Цель:** Обеспечить мгновенный откат на детерминированный парсер при сбоях LLM и сэкономить квоту/задержку на типовых запросах.
* **Область изменений:** `src/providers/yandex_llm.rs`, `src/search/mod.rs`, `src/http/search.rs`.
* **Изменения:**
  1. Внедрить паттерн **Circuit Breaker** для `YandexLlmProvider`: после $K$ последовательных таймаутов/ошибок 5xx запросы сразу фолбэкаются на детерминированный парсер в течение времени восстановления (cooldown).
  2. Добавить bounded LRU-кэш распознанных интентов (in-memory, e.g. 1 000 самых частых нормализованных запросов со скользящим TTL).
  3. В конфигурации поддержать явное указание версии модели вместо обязательного хардкода `/latest`.
  4. Добавить ограничение частоты запросов (per-client / IP rate limit) на эндпоинт поиска.
* **Acceptance criteria:**
  - При недоступности LLM время ответа поиска не превышает 200 мс (за счет размыкателя цепи).
  - Повторный запрос «включи рок» возвращает интент из кэша за <1 мс без сетевого запроса к Yandex.
* **Тесты:** Тесты с имитацией таймаута провайдера, срабатывания Circuit Breaker и попадания в кэш.

## Фаза 3. Клиентский тракт и аудио (RockCast) (P1)

### Задача RC-VOICE-001: Качественный анти-алиасинг ресемплер и VAD (Репозиторий `rockcast`)
* **Проблема:** В `rockcast/src/voice/resample.rs` линейная интерполяция 48 кГц $\to$ 16 кГц без фильтра нижних частот (Low-Pass Filter на 8 кГц) зеркалирует высокочастотный спектр в речевой диапазон, создавая алиасинг и ухудшая точность распознавания речи (WER). Отсутствие VAD гонит до 60 с тишины.
* **Цель:** Обеспечить чистое аудио для STT без алиасинга и отсекать тишину до отправки на сервер.
* **Область изменений:** Репозиторий `rockcast`: `src/voice/resample.rs`, аудио-захват.
* **Изменения:**
  1. Заменить линейный ресемплер на полифазный фильтр или оконный sinc-фильтр (например, с использованием качественного проверенного аудио-крейта `rubato` или легковесного FIR-дециматора с частотой среза 7.5–8.0 кГц).
  2. Добавить локальный Voice Activity Detector (VAD) на основе энергии сигнала / пересечений нуля для ранней остановки стрима при тишине.
* **Acceptance criteria:**
  - Отсутствие эффекта зеркалирования спектра выше 8 кГц (проверяется тестом с синусоидой 12 кГц: на выходе 16 кГц она должна быть подавлена не менее чем на 40 дБ).
* **Тесты:** Юнит-тесты на подавление частот выше Найквиста в ресемплере.

## Фаза 4. Эксплуатация, качество и метрики (P2)

### Задача SRCH-009: Инкрементальный и пакетный бэкфилл эмбеддингов
* **Проблема:** `backfill_embeddings` пересчитывает все 17 000 станций последовательно с `batch = 1` при каждом перезапуске entrypoint в Docker Compose, что блокирует запуск на десятки минут.
* **Цель:** Сделать бэкфилл инкрементальным, быстрым и независимым от старта контейнера.
* **Область изменений:** `src/bin/backfill_embeddings.rs`, `src/search/embedding.rs`, `src/persistence/embedding_postgres.rs`, `migrations/`.
* **Изменения:**
  1. Добавить колонку `searchable_text_hash (varchar/bytea)` в таблицу `station_embeddings`.
  2. Выбирать для пересчета только станции, у которых запись в `station_embeddings` отсутствует (`WHERE NOT EXISTS`) либо хэш текста изменился.
  3. Реализовать батчинг инференса (пакетная токенизация и инференс пачками по 32–64 станции).
  4. Убрать автоматический запуск тяжелого бэкфилла из `entrypoint` рабочего контейнера в compose.
* **Acceptance criteria:**
  - При неизменном каталоге повторный запуск бэкфилла завершается за доли секунды (`processed = 0, updated = 0`).
* **Тесты:** Интеграционный тест: повторный прогон не генерирует повторные записи.

### Задача SRCH-010: Управление жизненным циклом и миграцией версий моделей
