# Дорожная карта качества поиска RockServer

Состояние плана сверено с кодом 2026-11-10. Сервер принимает текстовый запрос или распознанный голосовой транскрипт и возвращает ранжированные станции. Исправления записи и распознавания аудио в RockCast ведутся отдельно.

Персонализация по истории описана в [отдельном проекте](../listening-search-analytics-plan.md) и не входит в эту последовательность: сервер пока не собирает данные, нужные для такой выдачи.

## Текущее состояние

- `SRCH-001` выполнена: ONNX-инференс использует `spawn_blocking` и ограниченный пул сессий (`src/providers/onnx_e5.rs`). Парсер запроса и генерация его эмбеддинга запускаются параллельно (`src/search/service.rs`). Повторно реализовывать это не нужно.
- PostgreSQL объединяет ограниченные лексические и E5 ANN-кандидаты; подтверждено использование HNSW-индекса. Проверка пригодного потока и триграммного сходства происходит до лексического `LIMIT`. Векторный кандидат без лексического совпадения пока скрыт сервисным порогом `0.35`.
- Формула гибридного ранжирования находится в SQL: совместимый вектор получает ограниченный metadata-вклад `[0,1]`, а поиск без совместимого вектора сохраняет прежнюю шкалу метаданных.
- SRCH-004: язык станции становится жёстким фильтром только при явном однозначном маркере в запросе. Диагностический E5-классификатор дал 2/28 верных ответов на размеченных явных запросах и 0/20 ложных на запросах без языка; его вывод не устанавливает фильтр.
- SRCH-009: backfill выбирает отсутствующие/устаревшие векторы по model/version/dimension и SHA-256 исходного текста, возобновляется по station ID; импорт и backfill запускаются отдельно. При включённом LLM словарь жанров читается из `genre_hierarchy` для каждого запроса.
- Для `/api/v1/search` уже есть общий анонимный лимит запросов; тела запросов и ответов YandexGPT не пишутся в debug-лог. SRCH-008 добавил breaker для поискового LLM; серверного кэша интентов нет. Версия модели по умолчанию `/latest`, с опциональной фиксированной версией.

## Шаг 1 — SRCH-011: измерить исходное качество

1. Зафиксировать снимок каталога и 50–100 обезличенных запросов с ожидаемыми станциями: точные имена, жанры, настроения, синонимы, опечатки, смешанные языки и запросы без явного жанра. Отдельно пометить случаи, где релевантная станция не имеет общего слова или триграммы с запросом.
2. Запускать тот же набор через реальный PostgreSQL-путь поиска с зафиксированными ответами парсера и векторами, полученными одной закреплённой версией модели. Считать `Recall@5`, `Recall@10`, `MRR`, долю пустых ответов и задержку. Не выдавать тесты in-memory репозитория или случайные фейковые векторы за измерение качества SQL и семантики.
3. Записать исходные значения и правила принятия регрессий. До этого не назначать новые веса и «целевые» абсолютные проценты наугад.

**Приёмка:** повторный запуск на том же снимке даёт одинаковый порядок станций и одинаковые метрики качества; задержка фиксируется отдельно и может колебаться. Проверка, требующая PostgreSQL или модели, явно помечена как таковая и не подменяется обычным `cargo test`.

Первый диагностический набор находится в `tests/fixtures/search_eval_golden_set.json`: 50 предварительно размеченных запросов к закреплённому RockCatalog из 41 станции. Он проверяет механизм измерения, но не представляет полный производственный каталог. `cargo test --test search_eval` проверяет файл и расчёт метрик без БД. Для фактической оценки нужен **отдельный уничтожаемый** PostgreSQL, потому что тест очищает таблицу станций; задать `TEST_DATABASE_URL` и `ROCKSERVER_SEARCH_EVAL_DISPOSABLE=1`, затем выполнить `cargo test --test search_eval -- --ignored --nocapture`. По умолчанию это измерение только метаданных. Для семантического прохода дополнительно задать `ROCKSERVER_SEARCH_EVAL_WITH_ONNX=1`, локальные пути `ROCKSERVER_ONNX_MODEL_PATH`, `ROCKSERVER_ONNX_TOKENIZER_PATH` и `ORT_DYLIB_PATH`, запустить тест с `--features onnx-local`. Набор и релевантные станции требуют продуктовой сверки до использования как релизного порога.

Диагностический baseline от 2026-11-09 измерен дважды на отдельной PostgreSQL БД в Docker. Все 50 списков ранжированных ID и метрики качества совпали между проходами. Метаданные: `Recall@5=0.647`, `Recall@10=0.660`, `MRR=0.647`, 12 пустых ответов. С закреплённой локальной E5: `Recall@5=0.713`, `Recall@10=0.720`, `MRR=0.700`, 5 пустых ответов. Это сравнительная точка для SRCH-003, а не оценка качества на полном каталоге. Точные хэши активов и времена указаны в `docs/status.md`.

Для следующих шагов повторять тот же режим, каталог и модель: сравнивать общий и категорийный `Recall@5/10`, `MRR`, число пустых ответов и списки ID. Падение качества или новые пустые ответы требуют разбора конкретных запросов и явного обоснования до принятия изменения. Задержку сравнивать по нескольким проходам отдельно от детерминированных рангов; фиксированного порога по этому малому локальному набору пока нет.

## Шаг 2 — SRCH-003: исправить префильтр

В `src/persistence/postgres.rs` проверять доступный поток с `health <> 'degraded'` до отсечения кандидатов. Добавить триграммное сходство в предварительную оценку. Не менять одновременно итоговую формулу ранжирования.

**Приёмка:** при переполненном префильтре неработающие станции не вытесняют рабочие; близкое написание названия с поздним ID остаётся кандидатом. Интеграционные тесты PostgreSQL воспроизводят оба случая и сохраняют порядок страниц.

## Шаг 3 — SRCH-002: добавить векторный ретривер

Добавить ограниченную ветку ближайших эмбеддингов с `ORDER BY embedding::vector(384) <=> query::vector(384) LIMIT …` и объединить её с лексическими ID до итоговой оценки. Учитывать совместимые `model`, `version`, `dimension`, исключённые станции, язык/страну и пригодный поток. Число векторных кандидатов выбирать по результатам шага 1, включая сценарий, где верхние соседи недоступны. Если вектор отсутствует, сохранять лексическую выдачу.

**Приёмка:** станция без лексического совпадения находится по вектору; недоступные соседи не заполняют весь лимит; результаты с фильтрами и пагинацией стабильны. На каталоге рабочего масштаба проверить `EXPLAIN ANALYZE` с реальными параметрами: запрос использует подходящий HNSW-план или документированно укладывается в измеренный бюджет. Проверить и повторно используемый план SQL, если параметры влияют на применение частичного индекса.

Состояние 2026-11-09: отдельная E5/384 ANN-ветка SQL и PostgreSQL-тесты работают; metadata-only выдача не меняется. На 50 запросах к 41 станции E5 `Recall@5/10` вырос с `0.713/0.720` до `0.833/0.840`, `MRR` с `0.700` до `0.820`, пустые ответы сократились с 5 до 0; это диагностический каталог, не производственная оценка. При этом чисто векторный кандидат доходит до repository, но неизменённый `SearchService` убирает его: семантическая часть веса даёт максимум `0.30`, а сервисный порог — `0.35`. В пяти семантических и пяти явно посторонних запросах значения E5 similarity перекрылись, поэтому безопасный отдельный порог без калибровки не назначен. Завершение публичной pure-vector выдачи зависит от SRCH-005.

`EXPLAIN ANALYZE` на 3000 **синтетических векторах только для проверки плана** показал `Index Scan using station_embeddings_e5_small_hnsw_cosine_idx`, 40 соседей при `LIMIT 200`, `Execution Time: 1.160 ms` ([полный план](srch002-hnsw-plan.txt)). PostgreSQL использовал текущий `hnsw.ef_search=40`; это не доказательство получения 200 кандидатов или производственной задержки. В следующем этапе проверить настройку HNSW/итеративный поиск, постфильтрацию и реальный план с параметрами на каталоге рабочего масштаба.

## Шаг 4 — SRCH-005: согласовать ранжирование

Сравнить на наборе шага 1 нормированные баллы и слияние позиций (RRF). Выбрать один вариант по качеству точных и смысловых запросов. Удалить либо связать с продакшеном неиспользуемую `ranking.rs::hybrid_score`; обновить `MIN_RELEVANCE_SCORE` под выбранную шкалу. Сохранить детерминированную сортировку при равном балле и поведение без эмбеддинга.

**Приёмка:** наличие вектора само по себе не пропускает нерелевантную станцию через порог; точные названия не проседают; метрики шага 1 не ухудшились по согласованным категориям. Тест проверяет SQL-путь, а не только вспомогательную формулу Rust.

Состояние 2026-11-09: на одних и тех же raw PostgreSQL-кандидатах 50 запросов сравнили прежнее взвешенное слияние, ограниченный в `[0,1]` metadata-вклад и weighted RRF (`k=60`). Это **offline сравнение кандидатов**, не пользовательская метрика SearchService: ограниченный metadata-вклад сохранил candidate Recall@5/10/MRR `0.948/0.955/0.930`, RRF дал `0.923/0.965/0.897`, снизив MRR spoken `1.000→0.883` и Recall@5 пяти semantic probes `0.600→0.400`. Выбран прежний вес `0.70/0.30` с ограничением metadata только при наличии совместимого вектора; `hybrid_score` удалён как неиспользуемая Rust-формула. Полный PostgreSQL/SearchService прогон сохранил прежний E5 baseline `Recall@5/10=0.833/0.840`, `MRR=0.820`, exact `Recall@5=0.900`; metadata-only baseline не изменился.

Добавлены пять предварительно размеченных чисто смысловых перефраз и 20 явно посторонних запросов. Все пять перефраз пока дают пустой ответ; два из 20 негативных запросов уже давали ложный ответ по лексике («stock price», «directions to the airport»), а metadata-only не даёт ни одного. Релевантные перефразы имели E5 similarity `0.880–0.893`, посторонние запросы достигали `0.903`; порог, открывающий pure-vector, нельзя честно выбрать по этим данным. SRCH-002/005 остаются частичными до расширения и продуктовой сверки набора, калибровки или смены модели/формата в SRCH-006. Два лексических ложных ответа следует проверить при очистке запроса в SRCH-006; это не регрессия данного шага.

На 3000 синтетических векторах при 1500 degraded потоках и 1000 станциях с несовпадающим языком прежние HNSW-настройки дали 17 пригодных из 40 просмотренных соседей при `LIMIT 200` (`1.237 ms`); `ef_search=200` и `iterative_scan=strict_order` дали 200 пригодных из 607 просмотренных (`9.776 ms`). Это [полные планы EXPLAIN](srch005-hnsw-depth.txt), а не производственный latency budget. После production-инцидента 2026-11-10 принудительное увеличение глубины удалено локально: рабочий запрос снова использует pgvector defaults `40/off` до замера качества и задержки на полном каталоге. Этот компромисс может недобрать ANN-кандидатов при фильтрации; измерение остаётся открытым.

## Шаг 5 — SRCH-004: обезопасить фильтр языка

До семантической классификации проверять явный языковой маркер в запросе. Для явно запрошенного языка сохранять жёсткое ограничение; для неоднозначного указания не превращать догадку модели в жёсткий фильтр. Измерить ошибки 28 прототипов на запросах с языком и без него; менять шаблоны или пороги только по этому набору.

**Приёмка:** «включи джаз» не получает фильтр языка, «джаз на французском» его получает, обычная локаль STT не становится языком станции. Тесты охватывают ложные срабатывания и отсутствие результата классификации.

Состояние 2026-11-09: на закреплённой E5 28 существующих прототипов правильно определили лишь 2 из 28 явных английских формулировок; 26 пропустили, ошибок выбора другого языка не было. На 20 запросах без языкового указания ложных срабатываний не было. Это небольшой диагностический набор, не оценка всех языковых формулировок. Hard filter теперь определяется явной однозначной конструкцией в исходном тексте (`in French`, `French language`, `на французском`, `французский язык`, прежние `русскоязычный`/`англоязычный`), а не LLM, классификатором или STT locale. Неоднозначное упоминание двух языков не создаёт фильтр; классификатор оставлен только для диагностики явных запросов. OpenAPI и примеры нормализованного ответа отражают это правило.

## Шаги 6–8 — жизненный цикл эмбеддингов

**SRCH-009.** Хранить хэш исходного `searchable_text` и происхождение вектора; выбирать только отсутствующие или устаревшие записи. Сначала устранить полный пересчёт и обеспечить возобновляемый проход, затем измерить, нужен ли пакетный ONNX-инференс. Отделить запуск backfill от каждого полного импорта. **Приёмка:** повторный проход без изменений делает ноль инференсов; изменение станции обновляет только её вектор; прерванный проход продолжается без пропусков.

Состояние 2026-11-10: миграция `0027` добавила nullable SHA-256 исходного документа к строке вектора; старые строки с `NULL` один раз пересчитываются. Backfill получает только активные записи с отсутствующим или несовпадающим model/version/dimension/hash, а `station_id` служит keyset-курсором. При записи исходная строка блокируется и её хэш повторно проверяется: если текст изменился во время инференса, проход завершается ошибкой и следующий запуск подберёт документ снова. Импорт удаляет векторы только при изменении `searchable_text`. На отдельной Docker БД детерминированный тест подтвердил `2` оставшихся инференса после прерывания на второй станции, затем `0` без изменений и `1` после изменения текста одной станции; stale write был отвергнут. Проверка импорта подтвердила, что изменение homepage не удаляет вектор, а изменение имени удаляет. Deployment запускает import и backfill отдельными последовательными job до проверки готовности; локальный `fill-database.ps1` теперь оставляет backfill явной командой. Пакетный ONNX-инференс не добавлен без замера узкого места.

**SRCH-010.** По решению владельца смена версии проходит в окне обслуживания: остановить сервис, сохранить старые векторы и provider image для отката, полностью построить новую версию рядом, проверить покрытие активного каталога, HNSW и размеченное сравнение качества, затем запустить сервис с новым provider. При ошибке или регрессии остановить сервис и запустить старую версию. Бесшовный hot switch не требуется. **Приёмка:** частичная новая версия не проходит проверку готовности; полная проходит только с индексом и явным отчётом о качестве; после возврата старого provider прежние векторы и ранги доступны.

Состояние 2026-11-10: миграция `0028` добавила общий HNSW индекс для E5/384 независимо от версии, сохранив индекс `onnx-v1`; ANN SQL принимает версию из фактического query embedding provider. Старт сервера с E5 проверяет, что у каждой активной станции есть вектор этой provenance с совпадающим SHA-256 текста и что готов индекс с выражением и predicate, используемыми ANN SQL. Для версии после `onnx-v1` дополнительно требуется явный JSON-отчёт с baseline/candidate Recall@5/10, MRR, пустыми ответами, хэшем набора, решением и именем reviewer. Оператор проверяет метрики; автоматического произвольного порога нет. На отдельной PostgreSQL БД с двумя детерминированными 384-мерными версиями частичная `onnx-v2` дала покрытие 1/2 и не прошла gate; выдача `onnx-v1` не изменилась. После полной сборки `onnx-v2` дала 2/2 и другой порядок, возврат provider `onnx-v1` восстановил прежний порядок. Forced EXPLAIN подтвердил доступность нового HNSW для version-параметризованного ANN выражения; это не оценка плана на реальном масштабе. Реальную новую модель не устанавливали и production switch не выполняли.

**SRCH-006.** Отдельным экспериментом сравнить сырой запрос с очищенным от командных слов и текущий `searchable_text` с более связным описанием станции. Изменение формата документа повышает версию предобработки и требует backfill из SRCH-009/010. **Приёмка:** новый формат внедряется только при улучшении эталонных метрик без потери точных названий и других категорий; иначе эксперимент закрывается без изменения продакшена.

Состояние 2026-11-10: opt-in тест сравнил четыре сочетания на закреплённой E5, 41 станции, 50 основных запросах, пяти дополнительных смысловых перефразах и 20 посторонних запросах. Очищение только ведущих командных слов не изменило итоговые Recall@5/10/MRR: `0.813/0.820/0.810` на 50 основных запросах. Связный документ станции оставил Recall@5/10 теми же, но снизил MRR до `0.807`. На всех 55 положительных запросах каждый вариант дал Recall@5/10 `0.739/0.745`, шесть пустых ответов; MRR составил `0.736` для текущего документа и `0.733` для связного. Exact-name Recall@5 сохранился `0.900`, genre `0.711`, spoken `1.000`; 20 посторонних запросов дали те же два ложных ответа во всех вариантах. На уровне сырых кандидатов связный документ менял часть рангов, но не улучшил пользовательскую выдачу. Эксперимент закрыт без смены рабочего формата, версии предобработки или backfill. Контрольные `0.813/0.820` ниже прежних `0.833/0.840`: после SRCH-004 исходный запрос `German language rock music` ставил одновременно фильтры языка станции `de` и страны `DE`, а размеченная станция имела `language: null`. Последующая проверка [официального описания потока](https://www.rockantenne.de/rockhoeren/streams/deutschrock) подтвердила немецкие тексты песен, но не язык речевого вещания. Поэтому 50-query fixture теперь содержит `deutschsprachige Rockmusik` с той же обоснованной меткой, без обоих hard filters; catalog metadata и SHA-256 оставлены без изменений. Повторный baseline в отдельной disposable PostgreSQL БД остался `0.813/0.820/0.810` с E5 и `0.647/0.660/0.647` без эмбеддингов: уточнённый запрос по-прежнему даёт пустой результат из-за существующего порога для чисто семантического совпадения. Это ограничение SRCH-002/005, а не эффект формата E5; для смены порога нужны более широкий каталог и сверенные метки.

## Шаги 9–10 — интент и внешний провайдер

**SRCH-007.** Передавать LLM актуальный контролируемый словарь `GenreTaxonomy` из БД и использовать его же при валидации ответа. Определить поведение при недоступной таксономии. **Приёмка:** добавленный жанр появляется в промпте и JSON-схеме без пересборки; недопустимый тег по-прежнему отвергается.

Реализация 2026-11-10: при включённом LLM сервис читает ограниченный (не более 2048 строк) снимок `genre_hierarchy` перед вызовом парсера и передаёт тот же объект в промпт, JSON-схему, локальную проверку ответа и жанровый fallback. Следующий запрос видит изменения БД без пересборки. При ошибке чтения, пустом или некорректном словаре весь запрос использует builtin-словарь. Детерминированный режим не добавляет SQL-запрос на таксономию. Фейковый тест подтвердил смену словаря между запросами, единство prompt/schema/валидации и отказ от неизвестного тега. Live PostgreSQL тест на отдельной disposable `rockeval_srch007_tests` подтвердил появление нового жанра после INSERT без пересборки.

**SRCH-008.** После серии таймаутов/ошибок провайдера временно пропускать вызов LLM и использовать существующий детерминированный парсер. Затем измерить пользу небольшого кэша интентов с ограничением размера и времени хранения; не хранить сырые голосовые команды без согласованной политики данных. Разрешить фиксированную версию модели вместо обязательного `/latest`. Существующий общий лимит `/api/v1/search` сохранить; необходимость лимита на клиента решать по измеренной нагрузке. **Приёмка:** при открытом circuit breaker нет внешнего вызова; после восстановления он возобновляется; тесты не обращаются к реальной сети.

Реализация: три подряд временных сбоя провайдера (timeout/transport, HTTP 429/5xx) открывают breaker на 30 секунд. После паузы допускается один пробный вызов; остальные запросы получают детерминированный fallback. Успешный probe закрывает цепь, временная ошибка продлевает паузу. Некорректный JSON/тег и HTTP 4xx кроме 429 не считаются временными сбоями. `YANDEX_LLM_MODEL_VERSION` принимает фиксированный идентификатор; пустое значение сохраняет `/latest`. Кэш не введён, поэтому этап частичен: доступный диагностический набор из 50 заранее размеченных запросов не отражает повторяемость голосовых команд в работе, а живых обезличенных данных о hit-rate, задержке и стоимости нет. Ключ из команды потребовал бы согласованной политики хранения. При SRCH-012 можно измерить только агрегированные доли повторов без записи текста и затем оценить bounded TTL. Общий лимит поиска сохранён; per-client лимит не обоснован замерами.

## Шаг 11 — SRCH-012: наблюдать и выпускать

Проверить все места записи поискового текста в логи, в том числе обычный текстовый поиск и голосовой приватный путь. Добавить агрегированные показатели задержки, ошибок и fallback LLM/ONNX, доли пустой выдачи и использования векторной ветки. Сравнить этапы с базой шага 1 на одинаковом каталоге и включать новый поиск поэтапно с возможностью отката.

**Приёмка:** голосовые команды не оказываются в логах без явно согласованного режима; метрики доступны операторам; после выпуска видны качество, задержка и причины перехода на fallback. Ограничения измерения и способ отката записаны в `docs/status.md`.

Локальная реализация 2026-11-10: SearchService пишет агрегируемое JSON-событие на завершённый поиск без текста/терминов; HTTP таймауты отмечаются отдельно. Доступ операторов — через существующий stdout/rolling file, без нового публичного endpoint. Повторяемость команд остаётся открытой до согласования политики данных. Production rollout и проверка после выпуска не выполнены; ограничения и откат — в `docs/status.md`.
