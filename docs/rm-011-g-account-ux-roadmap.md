# RM-011-G — Один аккаунт, несколько понятных устройств

**Статус:** планирование. Реализацию по этому документу не начинать без отдельного решения.

## Проблема

Текущий контур passkey и pairing технически умеет создавать учётные записи и сессии, но не
формирует понятный пользовательский сценарий. Пользователь воспринимает RockCast и RockMobile
как отдельные аккаунты, создаёт несколько passkey с неразличимыми UUID и не может понять, к
какому аккаунту или устройству относится подтверждение в браузере.

Это блокирует реальную интернет-бету: пользователь должен суметь подключить ПК и телефон к
одному аккаунту без токена, UUID, ручного поиска в Google Password Manager и догадок.

## Цель

Построить один простой сценарий:

```text
Первое приложение
    -> «Создать Rock-аккаунт»
    -> passkey
    -> первое устройство подключено

Каждое следующее приложение
    -> «Подключить это устройство»
    -> «Войти с passkey»
    -> «Подключить RockMobile / RockCast к аккаунту <имя>?»
    -> устройство появляется в едином списке
```

Аккаунт — это пользователь. RockCast, RockMobile и будущий ESP32 — устройства аккаунта, а не
отдельные регистрации. Анонимное радио продолжает работать без аккаунта и без RockServer.

## Непересекаемые правила

- Обычный пользователь не вводит UUID, Bearer token, URL сервера или технический код.
- Создание нового аккаунта — отдельное, явно подписанное действие; pairing не создаёт его молча.
- Browser pairing link всегда несёт контекст конкретного ожидающего устройства.
- Перед одобрением браузер явно показывает: имя аккаунта, тип/имя устройства и verification
  phrase. Пользователь подтверждает именно это устройство.
- Вход по passkey является discoverable/username-less: сервер определяет владельца по credential
  assertion и не доверяет `user_id` от браузера.
- Browser не получает native access/refresh tokens. Completion нативного pairing по-прежнему
  принимает только device/desktop proof, а owner определяется на сервере.
- Не ослаблять RP ID/origin validation, CSRF/cookie policy, Caddy-only trusted proxy, PostgreSQL
  rate limits, audit retention и лимит устройств.

## Подзадачи

### RM-011-G1 — Контракт аккаунта и pairing на RockServer

**Задача:** привести серверный контракт к модели «один аккаунт, много устройств».

- Завершить username-less passkey login: без поля account UUID; неизвестный credential,
  отменённый системный prompt и ошибки сервера возвращают понятные безопасные статусы.
- Добавить/зафиксировать пользовательские поля `account_display_name`, `device_display_name`,
  `device_type`, `created_at`, `last_seen_at` в DTO и хранилище там, где их ещё нет.
- Pairing request хранит и отдаёт достаточный контекст: целевой client type, предложенное имя
  устройства, короткий код, phrase, срок действия и безопасный статус.
- Сервер не позволяет одним endpoint создать аккаунт неявно при подтверждении device pairing.
- Добавить миграции, OpenAPI, unit/integration tests и негативные security tests.

**Готово, когда:** API способен отдать браузеру недвусмысленный объект «подключить это
устройство к этому аккаунту», а вход существующего пользователя не требует UUID.

### RM-011-G2 — Браузер: отдельные экраны «создать аккаунт», «войти», «подтвердить устройство»

**Задача:** заменить техническую стартовую страницу на один последовательный интерфейс.

- Экран pairing по secure link открывает только конкретный ожидающий запрос, а не общий экран
  подключения устройств.
- Если есть browser session, сразу показать аккаунт и карточку целевого устройства с действиями
  «Подключить» и «Отмена».
- Если сессии нет: дать два понятных выбора — «Войти с passkey» и «Создать Rock-аккаунт»;
  второй вариант визуально и текстом предупреждает, что создаст новый аккаунт.
- После успешного входа вернуться ровно к исходному pairing request.
- Убрать UUID и технические идентификаторы из основного интерфейса, не показывать native tokens.
- Статусы: ключ не найден, вход отменён, запрос истёк, устройство уже подключено, сервер
  недоступен. Тексты ориентированы на пользователя, не на HTTP-коды.

**Готово, когда:** по QR/deep link пользователь понимает, что он подключает, к какому аккаунту,
и не может случайно потерять контекст pairing после входа.

### RM-011-G3 — Центр аккаунта и устройств

**Задача:** дать пользователю единое место для понимания и управления доступом.

- Показать display name аккаунта и список устройств: `RockCast — Этот ПК`, `RockMobile — <модель>`
  вместо UUID.
- Показать client type, время подключения/последней активности и текущий статус сессии.
- Поддержать переименование устройства, logout текущего клиента и revoke другого устройства с
  ясным подтверждением действия.
- Показать лимит до 10 устройств и объяснить, как освободить место.
- Не выдавать в интерфейсе секреты, credential ID, refresh token или внутренние UUID.

**Готово, когда:** пользователь может глазами проверить, что Desktop и Mobile находятся в одном
аккаунте, и безопасно убрать лишнее устройство.

### RM-011-G4 — RockCast: ясное подключение ПК

**Задача:** адаптировать desktop UX к серверному контракту G1/G2.

- Действие называется «Подключить этот ПК к аккаунту», а не «зарегистрировать RockCast».
- Экран pairing показывает QR, deep link fallback, short code, phrase, предложенное имя ПК,
  отмену и понятный статус ожидания.
- После одобрения показать имя аккаунта и состояние «Этот ПК подключён».
- Экран Account & devices использует те же имена и доступные операции, что G3.
- Offline/anonymous playback не зависит от статуса аккаунта.

**Готово, когда:** первый запуск на ПК и повторная привязка не требуют токена или знания
устройства, уже отображённого в браузере.

### RM-011-G5 — RockMobile: ясное подключение телефона

**Задача:** адаптировать Android UX к тому же сценарию.

- Действие называется «Подключить этот телефон к аккаунту».
- При запуске browser link приложение сохраняет pairing context, ожидает результат ограниченное
  время и не создаёт новый аккаунт само.
- Экран после возвращения из браузера явно показывает `RockMobile подключён к <имя аккаунта>`.
- Account & devices использует те же display names, revoke/logout и anonymous fallback.
- Протестировать возврат из браузера, cancellation, timeout, rotation/revoke и отсутствие
  `user_id` в native completion.

**Готово, когда:** телефон можно добавить вторым устройством к аккаунту, созданному через
RockCast, одним browser/passkey подтверждением.

### RM-011-G6 — Очистка тестовых данных и миграционная политика

**Задача:** убрать путаницу от ранних тестовых аккаунтов без небезопасного слияния.

- Для staging подготовить отдельную администраторскую, документированную процедуру просмотра и
  удаления тестовых аккаунтов/сессий/устройств. Удаление выполняется только после явного
  подтверждения владельца staging.
- Не делать автоматическое объединение двух аккаунтов и не переносить устройства между ними без
  доказательства владения обоими аккаунтами.
- Отдельно описать, как пользователь удаляет старые passkey из Google Password Manager после
  удаления соответствующих тестовых аккаунтов.
- Для существующих production credentials обеспечить совместимость; их массовое переименование
  в системном менеджере ключей не обещать без подтверждённой platform API возможности.

**Готово, когда:** staging можно вернуть к одному чистому аккаунту без удаления данных по
догадке и без скрытого account merge.

### RM-011-G7 — Сквозная приёмка

**Задача:** проверить сценарий целиком, а не отдельные endpoint тесты.

Автоматически:

- API/OpenAPI, migration, WebAuthn negative cases, pairing state machine, CSRF/origin/proxy
  boundaries, rate limits, token redaction, refresh/logout/revoke.
- RockCast unit/build tests и RockMobile unit/build tests.
- Browser frontend typecheck/lint/build и e2e без реального credential assertion.

Вручную на staging с физическим телефоном:

1. После очищенного тестового контура создать один аккаунт через первый RockCast pairing.
2. Убедиться, что имя passkey и аккаунта различимы, а не представлены UUID.
3. Установить/запустить RockMobile, открыть pairing link, выбрать этот passkey.
4. Убедиться, что браузер показывает именно `RockMobile`, а подтверждение добавляет его к
   существующему аккаунту.
5. Проверить, что в devices видны и RockCast, и RockMobile; перезапуск сохраняет сессии.
6. Проверить logout и revoke устройства; анонимное радио должно остаться рабочим.

**Готово, когда:** все шесть пунктов повторяются без ручных токенов, UUID и неоднозначного
выбора устройства.

## Не входит в MVP этой задачи

- Управление воспроизведением RockCast с телефона (это отдельный remote-control контур).
- Автоматическое слияние случайно созданных аккаунтов.
- Синхронизация избранного/истории как условие успешного pairing.
- Установка/удаление системных passkey вместо штатного менеджера ключей ОС/браузера.

## Порядок реализации

`G1 -> G2 -> G4 и G5 параллельно -> G3 -> G6 -> G7`.

G1/G2 должны быть завершены до изменений клиентов: иначе пользовательский контракт останется
двусмысленным. G6 выполняется только после отдельного подтверждения на destructive очистку
staging-данных.
