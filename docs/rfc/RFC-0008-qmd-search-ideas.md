# RFC-0008: идеи гибридного поиска из qmd

- Статус: **Proposed** — версия программы не назначена (решение владельца: «сохранить в RFC пока»); пункты 1–6 GPU
  **не требуют**, пункт 7 — без GPU при облачной LLM
- Дата: 2026-10-14
- Автор: Claude (лид), по запросу владельца: «посмотри репозиторий qmd, что мы можем использовать у себя»
- Источник: [`tobi/qmd`](https://github.com/tobi/qmd) (MIT), просмотрен коммит `93d211f` от 2026-10-06
- Связано: ТЗ `docs/roadmap/ai-provider-architecture.md` (2.7, 6.8, 6.9, 6.10; этапы E0, E2, E6, E9); RFC-0002,
  RFC-0004, RFC-0005, RFC-0007

## Контекст

qmd — локальный поисковик по Markdown-документам (Node/Bun, SQLite FTS5 + sqlite-vec, модели GGUF в процессе через
node-llama-cpp). Схема поиска близка к варианту RFC-0009: несколько веток кандидатов → RRF (`k = 60`) →
переранжирование. Наш текущий порядок (ТЗ 6.8) — оценка `master` 0,70/0,30. Код нам не подходит (другой стек; модели в процессе противоречат решению 1 ТЗ), но несколько
приёмов переносятся на нашу архитектуру. Цифры и пороги ниже — значения qmd, не наши замеры.

## Предложение

Каждый пункт — **кандидат**: включается, только если на эталонных наборах (ТЗ 6.9) соблюдён порог качества ТЗ
(раздел 0, п. 7) и обязательные случаи проходят; иначе отклоняется. Пункты независимы.

### 1. Бонус за первое место в ветке (E9)

qmd после RRF добавляет +0,05 документу, занявшему 1-е место хотя бы в одной ветке, и +0,02 — за 2–3-е
(`src/store.ts:5402`). Причина: RRF размывает точное совпадение, найденное одной веткой, — его обгоняют документы,
средне найденные несколькими ветками.

Для нас: защита случая «точное название станции» (FTS/триграммы находят её первой, ANN — нет). Применим только вместе с RFC-0009 (RRF). Условие: бонус входит в
теоретический максимум нормировки (`rrf_max` по RFC-0009), чтобы `score` оставался в [0,1]; величины бонуса подбираются по
эталонам. Взаимодействие с совместной формулой (`w`, `p` — решение 15 ТЗ, RFC-0005) проверяется на тех же эталонах.

### 2. Пропуск LLM при сильном лексическом сигнале (E6, E9)

qmd сначала выполняет быстрый текстовый поиск; если лучший результат сильный (нормированная оценка ≥ 0,85) и отрыв от
второго ≥ 0,15, вызов LLM не делается (`src/store.ts:6291`). При заданном уточняющем контексте пропуск отключён.

Для нас: «включи Radio ROKS» не тратит вызов YandexGPT и бюджет поиска. Условия:
- лексический разбор не нашёл в запросе явных форм языка/страны, прилагательных национальности и отрицания (иначе
  фильтры от LLM нужны);
- пороги «сильный» и «отрыв» подбираются по эталонам на нашей шкале оценок;
- пропуск — только ожидания LLM; при параллельном запуске (ТЗ 2.7) вызов отменяется.

Метрика: доля запросов с пропуском, p95, число вызовов LLM.

### 3. Срезы метрик по веткам (E0)

Измеритель qmd (`src/bench/bench.ts`) прогоняет одни и те же эталоны отдельно по веткам: только текст, только вектор,
гибрид без переранжирования, полная цепочка — с P@k, recall, MRR, F1 и задержкой.

Для нас: скрипт метрик E0 дополнительно считает Top-k/MRR/Recall@k для каждого источника кандидатов отдельно (лексика,
ANN) и для итоговой оценки 6.8. Показывает, какая ветка даёт вклад, а какая шумит; базовая линия E0 — без изменений.

### 4. Разбор оценки результата (E9)

`--explain` в qmd прикладывает к результату вклад каждой ветки (ветка, позиция, вес, слагаемое RRF), бонус и итог.

Для нас: при формуле `master` разбор — `metadata_score`, `semantic_score`, веса, буст и итог (при RRF — слагаемые
веток). Такой разбор только в тестовом и админском режиме (не в публичном ответе, не в логах — ТЗ 6.10); нужен для
подбора порога, `w`, `p` и бонуса из п. 1.

### 5. Проверка дрейфа векторов (E2)

qmd хранит у вектора отпечаток (хеш модели, формата префиксов, параметров нарезки) и командой `doctor` пересчитывает
вектора нескольких сохранённых фрагментов, сравнивая с сохранёнными.

Для нас: версия и digest образа уже есть (ТЗ 2.2), но они не ловят пересборку образа без смены версии (например,
обновление ONNX Runtime тихо меняет вектора). Предложение: при старте фоновая задача E2 пересчитывает 3–5 станций и
сравнивает с сохранёнными с допуском (косинус; допуск — по замеру разброса на CPU). Несовпадение → режим без векторов
и ошибка в логе.

### 6. Смешивание с учётом позиции при переранжировании (к RFC-0002, RFC-0007)

qmd не заменяет порядок оценкой переранжировщика, а смешивает: для мест 1–3 после RRF позиция весит 75 %, 4–10 — 60 %,
дальше — 40 % (`src/store.ts:6507`). Переранжировщик может поднять кандидатов снизу, но не выбросить надёжные
совпадения из верхушки.

Для нас: закрывает риск «переранжировщик ломает точные совпадения» в RFC-0002 и RFC-0007. Принимается вместе с
одним из них; веса — по эталонам.

### 7. Переформулировка запроса через LLM (отдельный контракт)

qmd просит модель выдать варианты запроса по веткам: `lex` (ключевые слова → текстовый поиск), `vec`
(переформулировка → вектор), `hyde` (выдуманный подходящий документ → вектор); исходный запрос весит ×2. Модель —
своя дообученная Qwen3-1.7B (`finetune/`).

Для нас: расплывчатые запросы («что-нибудь для пробежки», «спокойное на ночь») вектор по исходному тексту ищет плохо.
Сервис LLM мог бы возвращать ещё `vec`-переформулировку (или `hyde` — короткое описание подходящей станции). Цена:
- векторная ветка ждёт LLM (сейчас параллельно, бюджет вектора запроса 300 мс — решение 14 ТЗ);
- меняется контракт `/intent` (новая версия `/v{L}`);
- правило «вектор запроса — по `raw_query`» (ТЗ 2.7, аудит №6) для этой ветки пересматривается.

Порядок: сначала облачная LLM текущего провайдера; своя дообученная модель — следующая версия (RFC-0004).

## Что не берём

Нарезку документов на фрагменты (описания станций короткие); SQLite/sqlite-vec (у нас PostgreSQL/pgvector); модели в
процессе (решение 1 ТЗ); MCP-сервер; поддержку CJK в FTS.

## Как решаем

По каждому пункту отдельно:
1. эталонные наборы (ТЗ 6.9): порог качества по языкам и классам, обязательные случаи проходят;
2. п. 2: p95 от Commit не растёт, число вызовов LLM снижается, ни одного случая потери фильтра языка/страны;
3. п. 5: тест на фейковом эмбеддере, меняющем вектора без смены версии, — сервер уходит в режим без векторов;
4. п. 7: рост Top-5/MRR на классе «настроение/занятие» ≥ 3 п.п. при соблюдении бюджета поиска.

## Риски

- Пороги qmd подобраны для документов и шкалы BM25 SQLite; на нашей шкале и коротких описаниях станций они другие.
- Пп. 1, 2, 6 добавляют настраиваемые величины в ранжирование — без разбора оценки (п. 4) их сложно подбирать.
- П. 7 добавляет последовательную зависимость от LLM в векторную ветку и ещё один выход модели, который нужно
  валидировать.

## Зависимости
