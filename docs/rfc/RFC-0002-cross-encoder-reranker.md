# RFC-0002: переранжирование кандидатов кросс-энкодером

- Статус: **Proposed** — для **следующей версии программы** (требует GPU)
- Дата: 2026-10-11
- Автор: Claude (лид), по разбору статьи https://habr.com/ru/articles/1092432/
- Связано: ТЗ `docs/roadmap/ai-provider-architecture.md` (6.8, 6.9, этапы E0, E9); RFC-0001

## Контекст

По ТЗ (6.8) итоговый порядок станций даёт оценка `master` (0,70 · метаданные + 0,30 · сходство векторов; RRF — RFC-0009),
затем жанровый постфильтр и порог. Оценка складывает признаки по отдельности и не «смотрит» на пару «запрос — станция»
целиком.

В статье после гибридного поиска применяется кросс-энкодер **`bge-reranker-v2-m3`**: он оценивает каждую пару
«запрос — кандидат» и пересортировывает топ. По словам автора: около 2,5 ГБ видеопамяти; изменения порядка логируются
(«поднялось в топ-20 / выпало из топ-20»), чтобы видеть, помогает ли переранжирование на этих данных.

**Требует GPU**: кросс-энкодер на 30 пар «запрос — станция» на CPU не укладывается в бюджет поиска. Текущая версия
программы — только CPU, поэтому RFC относится к следующей версии (по RFC-0003 — вероятно, только для платного тарифа).

## Предложение

Новая задача в репозитории модулей — **сервис переранжирования** с версионированным API по общим правилам ТЗ (раздел 5):

```
POST /v{R}/rerank
{ "query": "<raw_query>", "language": "ru",
  "candidates": [{ "id": "...", "name": "...", "tags": [...], "language": "...", "country_code": "..." }] }   // до 30
→ { "version": R, "scores": [{ "id": "...", "score": 0.0..1.0 }] }
```

- Текст кандидата собирает сам сервис (как сервис эмбеддингов); `rockserver` его не знает.
- В `rockserver`: после итоговой оценки (6.8) и жанрового постфильтра топ-30 отправляется в сервис; итоговый порядок — по `score`
  переранжирования, при равенстве — по оценке 6.8, затем по `station_id`. `score` ответа API — от переранжирования (уже в [0,1]).
- Сервис недоступен или не уложился в бюджет → порядок по оценке 6.8 без переранжирования (без ошибки для клиента).
- Выключатель `ROCKSERVER_RERANK=on|off`; бюджет — часть сквозного дедлайна (ТЗ, раздел 5), отдельный таймаут 250 мс.

## Цена

- Ещё один вызов модели на каждый поиск; при 30 кандидатах на GPU — ожидаемо десятки–сотни миллисекунд (проверить).
- Ещё один сервис, модель и версия в эксплуатации.

## Как решаем

Принимаем, если на эталонных наборах для каждого языка:
1. порог качества ТЗ соблюдён, и Top-1 или MRR растёт не менее чем на 3 п.п. относительно выдачи без переранжирования;
2. обязательные случаи проходят;
3. p95 всего поиска остаётся в бюджете ТЗ (6.10) при 10 параллельных сессиях.

## Что берём сразу, без принятия RFC

Отчёт «поднялось / выпало» не требует модели: скрипт эталонов (E0) при сравнении двух конфигураций (база и изменение)
выводит по каждому запросу, какие станции вошли в топ-10 и какие выпали. Это нужно для оценки E2, E9, RFC-0001 и этого
RFC. Предлагается внести в ТЗ (этап E0) — отдельным решением владельца.

## Риски

- Кросс-энкодер обучен на текстах, а у нас короткие записи станций — выигрыш не гарантирован.
- Переранжирование может перекрыть точные совпадения названий; это должны поймать обязательные случаи эталонов.

## Когда

Следующая версия программы (с GPU); после E9 ТЗ, независимо от RFC-0001.
