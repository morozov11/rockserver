# RFC-0005: рейтинг популярности станций в выдаче

- Статус: **Proposed** — **текущая версия программы** (решение владельца 2026-10-14); GPU **не требует**
- Дата: 2026-10-13, редакция 2 — 2026-10-14 (основной источник — Radio Browser); редакция 3 — 2026-10-14 (ответы
  владельца: текущая версия, популярность общая, о включениях в Radio Browser не сообщаем)
- Автор: Claude (лид), по запросу владельца: «станции, которые часто слушают, должны быть выше в выдаче»; источник —
  решение владельца «брать популярность с Radio Browser»
- Связано: ТЗ `docs/roadmap/ai-provider-architecture.md` (6.8, 6.9, 6.10, этапы E0, E9, E10); RFC-0006

## Контекст

По ТЗ порядок станций определяется только релевантностью: оценка `master` 0,70/0,30, жанровый постфильтр, порог (6.8).
На запросы с множеством равнорелевантных станций («рок», «джаз») сверху может оказаться мёртвая или никому не нужная
станция, а известная — ниже.

Сигналы популярности:
- **Radio Browser** (каталог, из которого импортируются станции) отдаёт по каждой станции в том же JSON, который уже
  читает наш импорт (`/json/stations/search`, `src/providers/radio_browser.rs`):
  - `clickcount` — включения за последние 24 часа; один IP засчитывается один раз в сутки на станцию;
  - `clicktrend` — изменение `clickcount` за 2 дня;
  - `votes` — голоса; только растут; голосовать с одного IP можно раз в 10 минут.

  Импорт эти поля сейчас **не сохраняет**; импорт — разовая задача деплоя `catalog_seed` (`deploy/compose.yaml:66`, `master` `43eb468`), расписания нет.
- **Свои данные** (частично): история вошедших пользователей (`history_records`, `play_duration_ms`) и соединения
  ретранслятора `/api/v1/stations/{id}/stream` (RFC-0006). Все клиенты играют через ретранслятор (RR-003 выполнен
  в `master` 2026-10-16), но анонимных пользователей сервер по истории не различает, поэтому своих данных пока мало.

## Предложение

### 1. Основной источник — Radio Browser (с первого дня)

- Импорт начинает сохранять `clickcount`, `clicktrend`, `votes` по станции.
- **Ежедневное обновление счётчиков** отдельной лёгкой задачей, без полного импорта: запросы по нашим `stationuuid`
  пачками (`/json/stations/byuuid?uuids=…`), с описательным `User-Agent` (требование Radio Browser), ограниченной
  частотой, повторами и таймаутами. Отказ Radio Browser → остаются вчерашние значения (поиск не ломается). Задача —
  фоновая, не в пути запроса.
- Хранятся **ежедневные снимки** `clickcount` (`station_popularity_daily(station_id, day, rb_clicks, own_listens)`):
  `clickcount` — окно одних суток, разовый снимок шумный (случайный всплеск или провал дня).
- `votes` легко накрутить — в рейтинг **не входят** (только хранятся; использование — отдельным решением после
  замеров). `clicktrend` — только для отчёта, не в формуле.

### 2. Дополнительный источник — свои прослушивания (когда накопятся)

- Квалифицированное прослушивание — не меньше 30 с: `history_records` (`play_duration_ms` ≥ 30 с) и соединения
  ретранслятора ≥ 30 с. Не более одного прослушивания станции на слушателя (аккаунт) в сутки.
- В таблицу популярности попадает только суточная сумма по станции (`own_listens`); персональных записей подсистема
  не создаёт.
- Вес своего сигнала растёт с его объёмом: пока своих прослушиваний за 30 дней меньше порога (например 1 000 по всему
  каталогу — при принятии), он не учитывается.

### 3. Рейтинг

- `rb(s)` — среднее `clickcount` за последние 14 дней с затуханием (полураспад 7 дней); `own(s)` — сумма своих
  прослушиваний за 90 дней с затуханием (полураспад 30 дней).
- Каждый сигнал — логарифм, затем перцентиль по каталогу (∈ [0,1]); `popularity(s) = (1 − α) · pct(rb) + α · pct(own)`,
  `α = 0`, пока своих данных меньше порога, затем растёт до 0,5.
- Перцентиль, а не сырое число: несколько очень популярных станций не задавливают остальной каталог. Станция без
  данных Radio Browser — нейтральное значение 0,5 (как пустые поля в 6.8).
- **Популярность общая** (решение владельца): одно значение на станцию для всех слушателей, без разбивки по стране
  слушателя; свои прослушивания тоже суммируются по всем странам.
- Пересчёт — раз в сутки после обновления счётчиков, в колонку `stations.popularity`.

### 4. Встраивание в ранжирование

- Порог релевантности (6.8) применяется **до** учёта популярности: популярность никогда не выводит в выдачу
  нерелевантную станцию.
- Для прошедших порог — **одна совместная формула** с бустом прилагательного (решение 15 ТЗ, 6.8):
  `final = score · (1 − w + w · match) · (1 − p + p · popularity)` — множители, как у буста в 6.8, потому что `score`
  без вектора не ограничен [0,1]. Если принят RFC-0009 (RRF, `score` ∈ [0,1]) — аддитивная форма
  `final = (1 − w − p) · score + w · match + p · popularity`.
  - `w` — вес прилагательного по 6.8 (`w = 0`, если модификатора в запросе нет);
  - `p` — вес популярности (стартовое предложение 0,15), подбирается по эталонному набору; `w + p ≤ 0,4`;
  - популярность выключена → `p = 0`, формула совпадает с 6.8.
- Точное совпадение названия станции популярностью не перекрывается — это проверяют обязательные случаи эталонов.
- Выключатель `ROCKSERVER_POPULARITY=on|off`; при `off` — порядок ТЗ без изменений.

### 5. О включениях в Radio Browser не сообщаем

Решение владельца: `/json/url/{stationuuid}` не вызываем ни с сервера, ни с устройства. Наружу уходят только запросы
счётчиков по `stationuuid` (п. 1), без данных пользователей.

## Как решаем

Принимаем, если:
1. на эталонных наборах (ТЗ 6.9) по каждому языку соблюдён порог качества ТЗ (раздел 0, п. 7) и обязательные случаи
   проходят;
2. по онлайн-метрике (ТЗ 6.10, обезличенно): доля поисков, после которых слушают станцию из Top-1 не меньше 30 с, растёт
   за период наблюдения относительно периода до включения;
3. ежедневное обновление: отказ или медленный ответ Radio Browser не влияет на поиск (тест на фейке); запросы — с
   `User-Agent` и в пределах заданной частоты;
4. подсистема популярности не создаёт персональных записей: в её таблицах и в логах только обезличенные агрегаты
   (проверка); существующая `history_records` — вне этого RFC.

## Риски

- **Чья популярность.** `clickcount` — слушатели всех приложений на базе Radio Browser по миру, не наши пользователи;
  распределение по странам и вкусам смещено в сторону этой аудитории.
- **Самоусиление** (для своего сигнала): станции наверху слушают чаще. Ограничения — малый `p`, затухание, порог
  релевантности до популярности.
- **Зависимость от внешнего сервиса**: Radio Browser работает «без гарантий», лимиты запросов не опубликованы.
  Смягчение — раз в сутки, пачками, со вчерашними значениями при отказе.
- Популярное «вообще» не значит популярное у этого слушателя: в разных странах слушают разное. Принято осознанно
  (популярность общая); смягчение — малый `p` и порог релевантности до популярности.
- Эталонный набор статичен и не меряет пользу популярности — нужна онлайн-метрика, а значит и время наблюдения.

## Зависимости
