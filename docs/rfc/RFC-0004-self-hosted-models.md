# RFC-0004: собственные модели STT и LLM в контейнерах

- Статус: **Proposed** — для **следующей версии программы** (требует GPU)
- Дата: 2026-10-11
- Автор: Claude (лид)
- Связано: ТЗ `docs/roadmap/ai-provider-architecture.md` (6.4, 6.5, решение 7), RFC-0003

## Контекст

Архитектура ТЗ уже позволяет подключить свою модель как ещё одного провайдера: свой контейнер записывается в раздел
`stt` или `llm` файла провайдеров языка (`rock-llm-service/providers/<код>.yaml`) (основной или запасной). В текущей версии используются только облачные провайдеры
(SpeechKit v1, YandexGPT-lite) и только CPU.

Собственные модели распознавания речи (класса Whisper) и LLM (открытые модели через vLLM или аналог) в реальном
времени требуют GPU: на CPU распознавание и генерация не укладываются в бюджет голосового запроса (ТЗ 6.10).

## Предложение

- **STT**: контейнер с моделью класса Whisper (faster-whisper или аналог) как провайдер сервиса STT. Признак стрима — по
  возможностям реализации. Может стать запасным провайдером для ru/en (закрывает риск «нет запасного STT», ТЗ 1.1) или
  основным для языков без хорошего облачного провайдера.
- **LLM**: открытая модель за OpenAI-совместимым API (vLLM) как провайдер сервиса LLM; та же схема ответа (ТЗ 6.5) и
  закреплённая версия модели.
- Никаких изменений в `rockserver`: только записи в файлах провайдеров языков
  (`rock-llm-service/providers/<код>.yaml`) и развёртывание контейнеров.

## Как решаем

Для каждого языка и модели — на эталонных данных:
- STT: доля верно распознанных фраз на наборе записей не хуже облачного провайдера; p95 в бюджете ТЗ;
- LLM: порог качества ТЗ (раздел 0, п. 7) соблюдён; доля ответов по схеме ≥ 99 %; p95 в бюджете.

## Когда

Следующая версия программы (с GPU). Зависит от RFC-0003 (какому тарифу какие модели).
